## Part 1 - Baseline Stack, Security & SEO

## TL;DR
- **Standardize on Next.js 16.2.7 (App Router + React 19.2 + TypeScript strict + Tailwind v4), with a Turborepo monorepo hosting a shared shadcn/ui design system consumed by both the SEO-critical marketing site and the security-first internal tools.** The router, security posture, and design-token layer are identical across products; only the SEO/analytics modules differ, which is exactly what makes one SOP and one starter template viable across both product types.
- **Security is a build-time discipline, not a runtime afterthought:** enforce `server-only`, Zod at every boundary, nonce-based CSP via Proxy (formerly middleware), Arcjet/Upstash rate limiting, and stay on a patched version - Next.js shipped a CVSS 10.0 RSC RCE (CVE-2025-66478/CVE-2025-55182, Dec 2025, exploited in the wild) and a 13-advisory batch (May 2026); minimum safe versions are 16.2.6 / 15.5.18.
- **Keep it lean and measurable:** Knip in CI (depcheck/ts-prune are archived and now recommend Knip), the ponytail Claude Code plugin for AI-generated code minimalism, Lighthouse CI performance budgets, Sentry observability, and design tokens centralized in Tailwind v4 `@theme` so fonts/spacing/color/animation are tunable from one file.

## Key Findings

### 1. Next.js version and baseline setup
- **Latest stable: Next.js 16.2.7** (current on npm as of June 10, 2026; confirm with `npm show next version`). Next.js 16 became stable October 2025; Turbopack is now the default bundler for both `next dev` and `next build`; minimum Node.js is 20+ (Node 22 LTS recommended). React 19.2 is the App Router baseline, and the React Compiler reached stable in Next.js 16 (opt-in via `reactCompiler`, not on by default).
- **App Router for all new projects.** Pages Router is not deprecated but is legacy/maintenance-mode. App Router is recommended for SEO (Metadata API), RSC, streaming, and Server Actions. One caveat worth noting in the SOP: the RSC CVE cluster of late 2025/early 2026 affected App Router specifically (Pages Router was immune), so patching discipline matters more with App Router.
- **Scaffolding:** `npx create-next-app@latest --typescript --tailwind --eslint --app --src-dir --import-alias "@/*"`. Next 16.2 added agent-ready `create-next-app` templates.
- **TypeScript strict mode:** `strict: true`, plus `noUncheckedIndexedAccess` and `noImplicitOverride`. Consider `ts-reset` (Matt Pocock) for safer built-in types. Use T3 Env (`@t3-oss/env-nextjs`) + Zod for typed, validated environment variables (throws at startup on missing/malformed vars).
- **ESLint/Prettier:** Next 16 **removed `next lint`**; use ESLint flat config with `eslint-plugin-next` and the `next/core-web-vitals` preset (blocks unoptimized images and synchronous scripts at the code level). Prettier for formatting, or Biome/Oxlint for speed. Add Husky + lint-staged + Commitlint for git hooks.

### 2. Dependency minimalism
- **Knip (webpro-nl/knip) is the 2026 standard** - it finds unused files, exports, dependencies, and unlisted imports in one pass, ships ~150 framework plugins (including Next.js), has monorepo support and `--fix`, and is used by Vercel, Shopify, Sentry, TanStack, and Backstage. **depcheck and ts-prune are both archived (2024–2025) and now explicitly recommend Knip.** Per Vercel engineer Gary Tyr (@gary__tyr) on X (Jan 2, 2025), "Knip helped us delete ~300k lines of unused code at Vercel." Run `npx knip --reporter compact` in CI, escalating gradually from `--include dependencies` to failing on all findings.
- **Complementary:** `eslint-plugin-unused-imports` (within-file cleanup); depcheck only for a quick, focused dependency-only check.
- **Bundle auditing:** `@next/bundle-analyzer` (Next 16.1 also added an experimental built-in bundle analyzer); bundlephobia for pre-install size checks.
- **ponytail (DietrichGebert/ponytail):** a Claude Code plugin/skill (works across 16 agents) described as making "your AI agent think like the laziest senior dev in the room. The best code is the code you never wrote." Before writing code it forces a decision ladder: (1) Does this need to exist? YAGNI → (2) Already in this codebase? reuse → (3) stdlib does it? → (4) native platform feature? → (5) installed dependency? → (6) one line? → (7) only then the minimum that works. Per the project README, it delivers "~54% less code (up to 94%) · ~20% cheaper · ~27% faster · 100% safe" - the ~54% figure is the mean across 12 feature tasks (Haiku 4.5, n=4), measured on headless Claude Code sessions editing tiangolo's full-stack-fastapi-template and scored on the git diff (e.g., a date-picker task cut from 404→23 lines by reaching for a native `<input type="date">`); the 94% is the per-task ceiling where an agent over-builds. Crucially it is "lazy, not negligent" - trust-boundary validation, data-loss handling, security, and accessibility are never cut. Install in Claude Code: `/plugin marketplace add DietrichGebert/ponytail` then `/plugin install ponytail@ponytail`. Modes: lite/full/ultra/off; commands `/ponytail-review` (diff over-engineering review → delete list), `/ponytail-audit` (whole-repo), `/ponytail-debt`. MIT licensed. Complementary AI-lean tooling: `caveman` (terse-prose control) and Knip for the automated dead-code sweep after AI generation.
- **Dependency security:** Dependabot (zero-config, GitHub-native, wired to the GitHub Advisory Database, alerts auto-close on merge) or Renovate (90+ package managers, on-by-default Dependency Dashboard, grouping presets, strongest monorepo support) for update PRs. Add `npm audit --audit-level=critical` as a CI gate (it has ~80% false-positive noise at lower levels, which trains devs to ignore it). Add **Socket.dev** for supply-chain/malicious-package behavioral detection (CVE databases miss malicious behavior). Important: GitGuardian documented that Dependabot/Renovate auto-merge accelerated the March 2026 malicious `axios` package spread (first repo modified 5 minutes after upload) - **require human review on dependency PRs; do not blanket auto-merge.**

### 3. Frontend security
- **Rate limiting:** `@upstash/ratelimit` + `@upstash/redis` (HTTP/REST-based, works in the Edge runtime where Node TCP does not) is the default. Define per-purpose limiters (global sliding window 100/min, strict auth window e.g. 5/15min, AI-endpoint window e.g. 10/min) in the Proxy layer (`middleware.ts` was renamed `proxy.ts` in Next 16) and/or per Route Handler. Declare the limiter outside the handler so it caches while the function is "hot." **Arcjet** is the more integrated option (rate limiting + bot detection + email validation + WAF-style rules in one SDK; bundled in the ixartz boilerplate). Vercel Firewall/WAF for platform-level DDoS.
- **XSS / CSP:** Nonce-based strict CSP generated per request in `proxy.ts` (`script-src 'self' 'nonce-{nonce}' 'strict-dynamic'`), passed via an `x-nonce` request header and read in Server Components via `headers()`. This **requires dynamic rendering** (disables static optimization/ISR - a real trade-off). Next 16 also offers experimental SRI that keeps static generation intact - treat SRI as the performance-first option and nonces as the policy-first option. Avoid `dangerouslySetInnerHTML`; if unavoidable, sanitize with DOMPurify (`isomorphic-dompurify` for SSR). Roll out CSP in `Content-Security-Policy-Report-Only` first, then enforce; automate a CI diff so any new external script origin triggers review.
- **Data validation:** Zod is the standard for forms, Server Actions, API routes, and env vars. Use `safeParse`; treat all client input as hostile. Client-side validation is UX only, never a security control.
- **CSRF:** Server Actions have built-in protection (POST-only + Origin/Host header comparison + per-build closure encryption), **but this is NOT sufficient alone** - CVE-2026-27978 (March 2026) demonstrated an `Origin: null` bypass (from sandboxed iframes) fixed in 16.1.7. Configure `serverActions.allowedOrigins` in `next.config.js`. For custom Route Handlers, CSRF is manual - use `@edge-csrf/nextjs` or `next-safe-action`. Set `SameSite=Lax/Strict` on session cookies. Every Server Action must independently **authenticate + authorize + validate** in strict order (treat every `'use server'` function as a public POST endpoint reachable by curl); a passing Zod schema is validation, not authorization. Arguments passed via `.bind()` are NOT encrypted.
- **Secrets / env vars:** Only `NEXT_PUBLIC_`-prefixed vars reach the browser (inlined into the JS bundle at build time). **Never destructure `process.env` and never use dynamic keys** (`process.env[key]`) - both break the static replacement and silently return undefined. Use the `server-only` package to hard-fail builds if server modules leak into client bundles; route data through a Data Access Layer returning minimal DTOs. Secret managers: Vercel env vars (default, scoped per environment via `vercel env pull`), Doppler, Infisical, AWS Secrets Manager. **Proxy all third-party API calls that use secret keys through Server Components/Route Handlers - never the client.** Set a stable `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` for multi-instance/self-hosted deploys. Scan with `@snytch/nextjs` for server/client boundary violations (GitGuardian's 2026 report found 28.6M secrets in public commits in 2025, +34% YoY).
- **Security headers checklist:** `Content-Security-Policy`, `Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` (or `frame-ancestors 'none'` in CSP), `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()`, `X-DNS-Prefetch-Control`. Use `next-secure-headers` or set them in `next.config.js` `headers()` / `proxy.ts`.
- **Notable CVEs (past ~15 months) - all verified against NVD, GitHub Advisories, and the Vercel/Next.js changelogs:**
  - **CVE-2025-29927** (March 21, 2025, CVSS **9.1**) - middleware authorization bypass via the internal `x-middleware-subrequest` header (skips middleware entirely). Affected 11.1.4 → up to the patches; **patched 12.3.5 / 13.5.9 / 14.2.25 / 15.2.3.** Vercel/Netlify-hosted apps unaffected; otherwise strip the header at proxy/WAF.
  - **CVE-2025-66478 / CVE-2025-55182** (Dec 3, 2025, CVSS **10.0**) - "React2Shell" RSC "Flight" deserialization → unauthenticated RCE via a single crafted POST. **Exploited in the wild** from ~Dec 5 (coin miners, cloud-credential harvesting). Affects App Router 15.x/16.x (not Pages Router, not 13.x/14.x stable). **Patched across 15.x (e.g., 15.5.7) and 16.0.7**; React fixes 19.0.1/19.1.2/19.2.1. Vercel advised rotating all secrets post-patch. (NVD later marked 66478 a duplicate of 55182 - report both; scanner hits are legitimate.)
  - **CVE-2025-55184** (RSC Denial of Service, **7.5**) and **CVE-2025-55183** (source code exposure, **5.3**) - Dec 2025 RSC follow-ups. A further related DoS, CVE-2026-23864 (7.5), followed Jan 26, 2026.
  - **Next.js "May 2026 security release"** (~May 6, 2026) - **13 coordinated advisories** across DoS (including upstream React CVE-2026-23870, GHSA-8h8q-6873-q5fj; plus Cache Components connection-exhaustion and Image Optimization DoS), middleware/proxy bypass (segment-prefetch auth bypass GHSA-267c-6grr-h53f; dynamic-route-param injection; Pages Router i18n default-locale bypass), SSRF via WebSocket upgrades on self-hosted Node (GHSA-c4j6-fc7j-m34r; can reach cloud metadata), cache poisoning, and XSS (CSP-nonce and beforeInteractive-script vectors). **Patched 15.5.18 / 16.2.6**; React `react-server-dom-*` 19.0.6/19.1.7/19.2.6. No 13.x/14.x patches - WAF cannot reliably block these; patching is the only complete fix.
  - **CVE-2026-27978** (March 16, 2026, **5.3**) - Server Actions `Origin: null` CSRF bypass; **patched 16.1.7** (companions CVE-2026-27977 dev HMR websocket null-origin, CVE-2026-27980 disk-cache DoS).
  - **CVE-2024-46982** ("Stale Elixir," Sept 2024, 7.5) - Pages Router cache poisoning (non-dynamic SSR routes), escalatable to stored XSS; **patched 13.5.7 / 14.2.10.**
  - **Minimum safe version: 16.2.6+ (or 15.5.18 on the 15.x line). Next.js 13.x and 14.x are unsupported for the 2026 fixes - the only remediation is upgrading to a patched 15.x/16.x.** Treat RSC advisories as an ongoing supply-chain surface (55182→55184/55183→23864→23870 all live in the same React Flight deserialization path) and keep `react-server-dom-*` current.

### 4. Code reusability and modular architecture
- **Feature-based structuring + colocation:** organize by feature/domain (`features/auth`, `features/billing`) rather than by file type; colocate components, hooks, tests, and server actions with their feature. Use App Router route groups `(marketing)`, `(app)` for layout/access separation. `src/` dir + `@/*` import alias.
- **Design system:** shadcn/ui as the base layer - copy-paste, you own the source (Radix primitives + Tailwind); it has crowded out MUI/Ant/Chakra for greenfield SaaS in 2026, and "owning your component source is now the default path." It themes via CSS variables, which maps cleanly to the token architecture in §5. Apply atomic-design layering (primitives → composed components → feature blocks).
- **Storybook** for component documentation and isolated development.
- **Monorepo:** Turborepo (Rust-based, from Vercel) is the default for sharing a design system across products; Nx is the heavier enterprise alternative. shadcn/ui has first-class monorepo support (`npx shadcn init --monorepo` scaffolds `apps/` + `packages/ui`; the `@workspace/ui` package owns Tailwind v4 config/tokens/`globals.css`, and apps only consume). Key wiring: `transpilePackages` for the UI package, a single Tailwind config in the UI package with `@source` directives scanning both `apps/**` and `packages/ui/**`, and `components.json` aliases pointing `ui` at `@workspace/ui`.

### 5. Global CSS, design tokens and theming
- **Tailwind v4 CSS-first `@theme` is the single source of truth.** Define all tokens (color in OKLCH, font family + type scale, spacing base unit, radius, shadow, animation duration/easing) in a CSS `@theme` block; Tailwind auto-generates utilities AND exposes them as native CSS variables for custom CSS and third-party code. This collapses the JS-config/CSS-variable duplication of v3 into one file. v4 also delivers ~5× faster full builds and 100× faster incremental builds.
- **Layering:** three token layers - base (raw values) → semantic (purpose-driven: `--color-surface`, `--color-text-primary`, `--duration-normal`) → component variants. For multi-platform/multi-tenant/Figma-sync needs, add a DTCG JSON layer compiled via Style Dictionary (Tailwind becomes one compiled output); for a single-brand web product, `@theme` + CSS variables alone are enough - the JSON layer is overhead until a second consumer exists.
- **Dark/light theming:** `next-themes` for the toggle; define semantic tokens once and remap their values under `:root` / `.dark` (or `data-theme`) rather than littering markup with `dark:` variants. CSS variables flip the entire theme with one selector override, respond at runtime, and avoid FOUC/flash.
- **Animation:** centralize duration/easing/stagger tokens in `@theme` (`--duration-fast/normal/slow`, `--ease-out/in-out/spring`, `--stagger-base`). Use `tailwindcss-animate` (or Tailwind v4's `@starting-style` variant) for simple enter/exit transitions and Framer Motion (`motion`) for complex orchestration; have both reference the CSS-variable tokens so timing is tunable sitewide from the theme block. Prefer `transform`/`opacity` animations (off main thread) for CLS/INP.

### 6. SEO
- **Metadata API:** static `metadata` object or async `generateMetadata()` in `layout.tsx`/`page.tsx` (Server Components only; you cannot export both from one segment). Set `metadataBase: new URL(...)` in the root layout (without it, relative OG/canonical URLs break social previews), title `template`/`default`, `alternates.canonical` on every page (self-canonical for paginated archives), and `robots` per-route (noindex preview/auth routes). Metadata cascades and merges down the layout tree; `fetch` inside `generateMetadata` is memoized.
- **Dynamic OG images:** `ImageResponse` from `next/og` via `opengraph-image.tsx` / `twitter-image.tsx` file conventions, or an `/api/og` route; 1200×630. `generateImageMetadata` for multiple images per route. Warm the CDN cache after publishing.
- **JSON-LD structured data:** inline `<script type="application/ld+json">` with `JSON.stringify` in the page/layout - Organization, SoftwareApplication, Product, FAQPage, BreadcrumbList. Validate with Google's Rich Results Test.
- **sitemap.xml / robots.txt:** native App Router `app/sitemap.ts` and `app/robots.ts` (typed `MetadataRoute.Sitemap` / `MetadataRoute.Robots`, no physical file needed). For >50,000 URLs export `generateSitemaps()` for automatic chunking (`sitemap/0.xml` + index). `next-sitemap` is the alternative for static-export/heavier config (`generateRobotsTxt`, `sitemapSize`, `alternateRefs`).
- **Core Web Vitals (a confirmed ranking factor):** `next/image` (auto WebP/AVIF, responsive srcset, lazy load, layout-shift prevention via intrinsic dimensions, `priority` on the LCP image), `next/font` (self-hosted, `display: swap`), `next/script` with strategy (`afterInteractive`/`lazyOnload`). Keep primary content in Server Components - most AI crawlers don't execute JavaScript, so `useEffect`-fetched content is invisible to them. Publish accurate `lastmod` timestamps (AI systems use sitemap freshness as a recrawl signal).

### 7. Analytics
- **For the marketing site, the pragmatic 2026 stack is Plausible + PostHog.** Plausible is cookieless, DPDPA/GDPR-friendly (no consent banner in most cases), and per Plausible.io its script is "less than 1KB... roughly 45 times smaller than Google Analytics," loads async in one request, with "no negative effect on your Core Web Vitals" - ideal for traffic/referrer/conversion-goal tracking. PostHog handles product behavior (funnels, session replay, feature flags, A/B); its free tier (posthog.com/pricing) includes 1M events, 5K session replays, 1M feature-flag requests, 100K error-tracking exceptions, and 1,500 survey responses per month, resetting monthly, with unlimited team members and 1-year retention. Vercel Web Analytics is the zero-config option if already on Vercel (50K events free on Hobby; adds Speed Insights for CWV). GA4 only if you need native Google Ads integration - it samples data above a few hundred thousand sessions, requires consent, is DPA-heavy, and several EU DPAs have ruled against configurations.
- **Conversion/funnel tracking:** define ~5 critical events (`signup_started`, `signup_completed`, `cta_clicked`, `demo_requested`, `plan_upgraded`) in PostHog; layer UTM tracking + Search Console integration for attribution. Deploy PostHog behind a reverse proxy on your own domain to avoid ad-blocker interception.
- **India DPDPA (Digital Personal Data Protection Act, 2023):** consent-centric (unlike GDPR's six legal bases). DPDP Rules notified Nov 13, 2025; consent-manager registration opens Nov 13, 2026; full compliance by **May 13, 2027**. Per the Act's Schedule, penalties reach **up to ₹250 crore** for failure to take reasonable security safeguards (the top tier), ₹200 crore for failure to notify a breach, ₹200 crore for children's-data breaches, and ₹150 crore for Significant Data Fiduciary obligations - imposed per instance by the Data Protection Board of India (operational since Nov 13, 2025), with no statutory aggregate cap. Consent must be free, specific, informed, unconditional, with withdrawal as easy as granting, preceded by a plain-language privacy notice offered in English + Eighth Schedule languages. **Key nuance: DPDPA does not explicitly mention cookies and applies only to identifiable personal data** - aggregated/anonymized analytics (Plausible-style) largely falls outside its scope, so a clear privacy notice is best practice while granular cookie consent is not strictly mandated (India also permits a single blanket consent rather than GDPR-style per-purpose granularity). Use a registered Consent Manager/CMP only if you deploy identifiable tracking.

### 8. DNS, deployment and publish checklist
- **Local → staging → production separation:** separate env files (`.env.local` git-ignored and never deployed; `.env.production` committed but secret-free), separate deployment environments, secrets in the platform store (Vercel env vars scoped per environment / Doppler / Infisical). Give preview deployments a `noindex` header - un-noindexed Vercel previews get indexed and dilute authority.
- **DNS setup:** A record (apex → IP, or ALIAS/ANAME where supported), CNAME (`www` → platform host), TXT records (domain-ownership verification + SPF/DKIM/DMARC for email), optional CAA (restrict cert issuers). SSL/TLS is auto-provisioned (Let's Encrypt on Vercel/most platforms); enforce HTTPS + HSTS with `preload`.
- **Publish checklist:** prod env vars set + secrets rotated → `next build` passes on Node 22 → Lighthouse CI budget met → sitemap/robots live with correct domain → canonical + `metadataBase` set → OG images verified (share-preview test) → 404/500 pages present → analytics + consent live → Sentry DSN configured → security headers verified (securityheaders.com) → DNS propagated → SSL active → Search Console verified + sitemap submitted.
- Keep the SOP platform-agnostic (works on Vercel, Netlify, Cloudflare, or self-hosted Node via the Next 16 stable Adapter API) with Vercel as the default case. Note the SSRF/middleware CVEs above affect self-hosted Node deployments more than Vercel-hosted ones.

### 9. Ranking and growth-level optimization
- **Content/ranking:** comparison pages ("X vs Y"), use-case landing pages, and programmatic SEO (a template + a data source generating pages with unique metadata + canonical per page - but gate every generated page with quality validation, since Google penalizes thin AI content; the best programmatic systems use AI sparingly over solid data and templates). Hub-and-spoke internal linking to compound authority and improve crawl paths. Backlink basics (digital PR, guest content, directory/listing presence). Core Web Vitals at the 75th percentile removes a class of ranking ceilings.
- **Advanced concepts (likely new to intermediate devs):**
  - **Edge Middleware/Proxy for geo personalization** - region-based content/redirects at the edge before the app runs.
  - **ISR + streaming SSR** for performance at scale - revalidate on a schedule (product prices, indexes) instead of rebuilding; stream above-the-fold content first. Next 16 improved prefetch/navigation (layout dedup, incremental prefetch).
  - **Feature flags** - PostHog flags or OpenFeature; enables canary/ring/kill-switch releases. Track "flag debt" and clean up stale flags.
  - **Observability** - Sentry for error + performance tracking across all three runtimes (client/server/edge = 3 configs). Server Actions don't emit OpenTelemetry spans by default, so wrap them with `withServerActionInstrumentation`; production strips Server Action error detail from the client, so Sentry's server-side capture is the only way to see the real exception; use its HTML-diff view for hydration errors. Add structured logging (`pino`) and a `/api/health` probe endpoint.
  - **Performance budgets in CI** - Lighthouse CI (`.lighthouserc.json` asserting e.g. `categories:performance >= 0.9`, `categories:seo >= 0.9`) to block regressions before merge.
  - **Accessibility (a11y)** - a legal safeguard, a conversion lever, and an SEO signal. Radix/shadcn provide accessible primitives; test with axe + Playwright; use semantic HTML, keyboard nav, and visible focus states.
  - **A/B testing** - PostHog experiments, or edge-based flag splitting.

### 10. Responsive and multi-device support
- **Mobile-first Tailwind:** unprefixed utilities are the mobile base; `sm:`(640) `md:`(768) `lg:`(1024) `xl:`(1280) `2xl:`(1536) layer up (min-width). The common trap: `sm:` means "at the small breakpoint and up," not "on small screens" - style mobile with unprefixed utilities. Customize via `@theme` `--breakpoint-*` (use rem consistently). Google indexes mobile-first; touch targets ≥44×44px with generous padding.
- **Tablet:** usually the `md:` range; watch single→multi-column transitions and test both portrait and landscape.
- **Large screens / smart-TV:** cap content width (`max-w-*` + `mx-auto`, or add a `3xl` breakpoint) so line lengths stay readable - the Tailwind team's own guidance is that extra width beyond ~640px rarely earns a new column, so add breathing room rather than stretch. Smart-TV browsers are rare for a marketing site but benefit from the same max-width discipline plus large tap/focus targets and strong `focus-visible` states for D-pad/remote navigation (10-foot UI). Use container queries (`@container`) for component-driven responsiveness independent of viewport.
- **QA tooling:** Chrome DevTools device mode (free baseline), Responsively App / Sizzy (multi-device simultaneous view with hot reload - surfaces missing breakpoint prefixes instantly), BrowserStack (real-device cloud, cross-browser), Playwright for automated cross-viewport E2E. Always verify on at least one real phone (emulators miss touch/perf realities).

## Details

The security posture deserves emphasis given the internal-tools use case. The single most important operational rule is **version currency**. 2025–2026 saw an unusually dense series of RSC "Flight" deserialization vulnerabilities - CVE-2025-55182/66478 (RCE, CVSS 10.0, exploited in the wild), then CVE-2025-55184/55183, then CVE-2026-23864, then the May 2026 CVE-2026-23870 - all in the same React Server Components code path. This is effectively an ongoing supply-chain risk surface unique to the App Router. The SOP should mandate: (a) Renovate/Dependabot auto-PRs for `next` and `react-server-dom-*`, (b) a CI gate that fails builds on any high/critical advisory, (c) staying within the latest patch of the 16.x line (≥16.2.6), and (d) never auto-merging dependency PRs without human review (per the GitGuardian axios-worm finding).

For the internal tools where SEO is irrelevant, drop the Metadata/OG/sitemap/analytics modules - and the nonce-CSP-forces-dynamic-rendering trade-off becomes a non-issue, since internal tools render dynamically anyway (you can run the strictest nonce CSP without sacrificing anything). Everything else - `server-only` DAL, Zod at every boundary, rate limiting, the full security-header set, dependency hygiene, design tokens, responsive QA - carries over identically. That shared baseline is precisely what makes one SOP plus one bootstrapped starter template viable across both the marketing site and the internal business OS.

On the marketing side, the tension to resolve deliberately is strict-CSP vs static generation. A nonce-based CSP forces dynamic rendering, which costs you the CDN-speed static/ISR delivery that helps Core Web Vitals and SEO. For the marketing site specifically, prefer Next 16's experimental SRI or a hash-based CSP to preserve static generation, and reserve nonce-CSP for the few pages that genuinely need inline scripts.

## Recommendations

1. **Immediately (shared baseline):** Pin Next.js to latest 16.2.x (≥16.2.6), Node 22 LTS, TypeScript strict + `noUncheckedIndexedAccess`, ESLint flat config with `next/core-web-vitals`, Prettier, Husky/lint-staged/Commitlint, T3 Env + Zod for env validation, and `server-only` on all data-access modules. Add Knip to CI.
2. **Security layer (both product types):** Add Arcjet (or Upstash Ratelimit) for rate limiting, nonce-CSP or SRI via `proxy.ts` (Report-Only → enforce), `next-secure-headers` for the full header set, Zod on every Server Action/Route Handler with independent auth+authz, and configure `serverActions.allowedOrigins` + `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`. Wire Dependabot/Renovate + Socket.dev + `npm audit --audit-level=critical` as CI gates (human review required on dep PRs).
3. **Monorepo + design system:** Stand up a Turborepo with `@workspace/ui` (shadcn/ui + Tailwind v4 `@theme` tokens: OKLCH color, type scale, spacing base, radius, animation duration/easing) + Storybook + `next-themes`. Both the marketing site and internal tools consume it.
4. **SEO/growth (marketing app only):** Metadata API + `metadataBase`, dynamic OG via `next/og`, JSON-LD, `app/sitemap.ts` / `app/robots.ts`, Lighthouse CI budget in CI, Sentry, Plausible + PostHog.
5. **AI-code hygiene:** Install ponytail in Claude Code across the team (default `full` mode); run `/ponytail-audit` and `npx knip` before merges.
6. **Thresholds that change the plan:** a new critical Next.js CVE → patch within 24–48h; bundle/LCP regresses past the Lighthouse budget → block the deploy; the design system gets a second consumer (native mobile app or Figma sync) → introduce a DTCG JSON token layer via Style Dictionary; DPDPA enforcement (May 2027) approaches and you deploy identifiable tracking → register/deploy a Consent Manager/CMP.

## Caveats
- Version and CVE specifics are accurate as of July 10, 2026; Next.js patches very frequently - always confirm the current patch with `npm show next version` before pinning.
- Some cited sources are vendor blogs/marketing (Upstash, Arcjet, PostHog, boilerplate vendors) and SEO-content sites; treat GitHub star counts and "best-of" rankings as directional, not authoritative. Primary sources (nextjs.org, Vercel changelog, GitHub/NVD advisories, Tailwind docs) were prioritized for all factual claims, especially the CVE table.
- The nonce-based CSP vs static/ISR trade-off is real and unavoidable: strict nonce CSP forces dynamic rendering. Use SRI/hash-CSP on the marketing site to keep static generation; nonce-CSP is fine (and preferred) on the always-dynamic internal tools.
- DPDPA interpretation on cookies is still evolving - the Data Protection Board of India may issue future guidance, and the "aggregated analytics is out of scope" reading is the current mainstream interpretation, not a settled ruling. Sectoral rules (RBI/SEBI for fintech) can override DPDPA's cross-border flexibility.
- CVE-2025-66478's NVD "rejected as duplicate of CVE-2025-55182" status means scanners may flag either ID - both are legitimate; report them together.

## Cluster A - Trust, Compliance, Identity & Auth

Covers items #1, #10, #28, #14, #24. Part 1 already covers CSP, security headers, CSRF, and secrets - this cluster is the trust *surface*: consent, link hygiene, and passwordless auth.

### 1. Cookies (consent banner - or not)
For this exact stack, the honest 2026 answer is **you may not need a banner at all**. The only tracker installed is PostHog (Plausible from Part 1 §7 is cookieless by design). DPDPA gates *processing of identifiable personal data*, not storage-access itself - unlike the EU's ePrivacy Directive, India has no blanket "any non-essential cookie needs consent" rule. If PostHog is configured to never capture identifiable data, analytics falls outside DPDPA's consent trigger entirely:
```ts
posthog.init(key, {
  person_profiles: 'identified_only',
  disable_session_recording: true, // or gate it, see below
  respect_dnt: true,
  persistence: 'memory', // no durable cross-session identifier
});
```
Ship a Privacy Policy disclosure of PostHog usage instead of a banner - transparency, not a gate. If session replay or a non-essential tracker (ad pixel, chat widget) gets added later, build a minimal in-house banner (shadcn `Sheet`/`Dialog`, two toggles - Necessary / Analytics) rather than a heavy CMP like OneTrust/Cookiebot, which don't fit a brutalist, low-JS site. Write consent server-side to a first-party `httpOnly` cookie via a Server Action, read it in `proxy.ts` to decide whether to inject the PostHog snippet at all - scripts must be blocked *before* consent, not loaded then hidden, or the "no banner needed" argument stops being true. Note: if the EU/UK becomes a target market later, TCF 2.3 became mandatory (Feb 28, 2026) for any CMP wired to certified ad/analytics SSPs - irrelevant today with zero ad-tech in the stack, but revisit if that changes. Don't lump Arcjet's bot-detection/rate-limit signals into an "Analytics" consent category - that's a security function (DPDPA Sec. 7 legitimate-interest), not consent-gated telemetry.
**Page types:** All.

### 10. Privacy & Terms pages, security `rel` attributes, focus/active states as trust signals
**Privacy & Terms**: static routes (`app/(legal)/privacy/page.tsx`, `.../terms/page.tsx`), `export const dynamic = 'force-static'`, content in versioned MDX with a frontmatter `updatedAt` so legal edits don't need an engineering deploy. Reference the *actual* tools by name (Plausible, PostHog, Arcjet, Sentry) and what each collects - a generic template that doesn't match real data flows is itself a compliance gap, and must surface the DPDPA Grievance Officer contact per Part 1 §7.
**`rel` on `target="_blank"`**: modern browsers imply `noopener` semantics by default now, but only inconsistently across in-app/WebView browsers - keep writing `rel="noopener noreferrer"` explicitly regardless (self-documenting, zero cost); `noreferrer` isn't implicit anywhere and additionally strips the `Referer` header, useful when Cybercom links out to CVE databases or vendor advisories. Enforce via `eslint-plugin-react`'s `react/jsx-no-target-blank` with `{ enforceDynamicLinks: 'always', warnOnSpreadAttributes: true }` - CI-caught, not a review nit. `next/link` does **not** auto-add `rel` when passed `target="_blank"` - same rule applies.
**Focus/active states as trust, not just UX**: a security company's UI reading as "unfinished" (invisible focus rings, no press-state) undermines exactly the credibility the brand sells. Treat `:hover`/`:active`/`:focus-visible` as required on every interactive element - full token-driven implementation detail lives in item #40 below, this entry is the "why it's a trust signal, not just polish" framing.
**Page types:** All.

### 28. Noopener security sanitization (the enforcement layer)
The attack this closes: a `target="_blank"` page with `window.opener` access can silently rewrite the *originating* tab to a phishing clone (reverse tabnabbing). Item #10 covers the static-analysis control (`rel` attribute + ESLint rule) - this item is the runtime-sanitization half for content that bypasses static analysis: `dangerouslySetInnerHTML`, MDX-rendered blog/advisory content, or HTML echoed from a form. DOMPurify's default config does **not** strip or add `target`/`rel` from user-supplied HTML - route all such HTML through one sanitizer at the point it enters the render tree (`isomorphic-dompurify`, already installed, with `ADD_ATTR: ['target','rel']` forcing the attribute) rather than trusting the source. Add a CI check (Playwright + axe, or a plain DOM assertion) asserting `a[target="_blank"]:not([rel*="noopener"])` doesn't exist in rendered output - belt-and-suspenders on top of the static lint rule, since it also catches anchors built dynamically at runtime. Same rule applies to `rehype-external-links` config for any MDX pipeline (`target: '_blank', rel: ['noopener','noreferrer']`).
**Page types:** All - highest exposure on Landing/blog (CMS content) and Internal admin tools rendering user-submitted input.

### 14. Passkeys & biometrics + one-click social identity
**Library choice**: `@simplewebauthn/server` + `@simplewebauthn/browser` is the 2026 reference implementation (~4.9M weekly downloads combined) if building auth directly - wraps the WebAuthn ceremony behind `generateRegistrationOptions`/`verifyRegistrationResponse`/`generateAuthenticationOptions`/`verifyAuthenticationResponse`. Two Route Handlers (register/authenticate), server-issued challenge in an `httpOnly` cookie (never client state), persist the returned credential (public key + counter) on the user record. Budget ~30 minutes for the happy path, a day or two more for cross-device QR sign-in and account recovery without a passkey. If the team wants a batteries-included, self-hosted auth layer instead of building on raw SimpleWebAuthn (no third-party credential custody, which matters for this brand), **better-auth** + `@better-auth/passkey` is the pragmatic default - typed server/client hooks map cleanly onto App Router Route Handlers. Clerk is the fallback if the team wants a fully managed product instead and is fine with third-party credential custody.
**Conditional UI**: `autoComplete="username webauthn"` on the login field (the `webauthn` token must be last) + `startAuthentication({ useBrowserAutofill: true })` on mount surfaces passkeys in the native autofill dropdown - support (Chrome 108+, Safari 16+, Edge 108+, Firefox 122+) covers effectively all 2026 traffic, so make this the default login UI, not a secondary button. **Ship passkeys additive to password/email first** - don't force a hard cutover; deprecate passwords once adoption is high.
**Social identity**: Google's **FedCM became mandatory in August 2025** - the old cross-origin-iframe One Tap integration is deprecated; the browser (not the IdP script) now owns the account-chooser UI and only contacts the IdP after explicit consent, which changes the first-run conversion curve. Implement via better-auth's social provider config (abstracts the FedCM migration) rather than raw Google Identity Services if better-auth is already in use for passkeys.
**Arcjet integration**: rate-limit `/api/auth/passkey/*` and OAuth callback routes with Arcjet's `slidingWindow` rule (already installed); apply bot detection to any surviving password-fallback path.
**Gotchas**: `rpID` must match per environment (staging vs. prod) or cross-device testing silently breaks; a surviving password fallback remains the real weak point until retired; FedCM needs `connect-src`/`frame-src` CSP allowances for `accounts.google.com`.
**Page types:** SaaS, Internal (login-gated products); Landing only for a gated resource/demo signup.

### 24. Passkey payment auth (Secure Payment Confirmation)
SPC extends WebAuthn to authorize a *payment*, cryptographically binding the assertion to the exact transaction amount + payee - satisfies PSD2 RTS Article 5 "dynamic linking" (any change to amount/payee invalidates the signed challenge) inside the checkout page itself, no redirect to the bank's domain. **Honest 2026 status: Chromium-only** (desktop Chrome/Edge) - no committed Safari or Firefox support, Apple hasn't committed to it at all. This cannot be a primary payment-auth path yet, only a progressive enhancement layered over the existing 3DS/OTP flow, which stays the fallback for every non-Chromium visitor. **Recommendation: watch-and-prototype, don't build.** Don't hand-roll `PaymentRequest`/SPC for a production checkout - if a paid product ships, Stripe (or the chosen PSP) already wraps equivalent step-up/3-DS authentication internally, and single-browser support gives poor payback on the integration cost. If a dedicated need emerges later (e.g., cryptographic transaction evidence for high-value B2B invoicing), `@simplewebauthn/server`'s SPC helpers can reuse the same credential store built for #14. Revisit when SPC reaches full W3C Recommendation status or a second browser engine ships support.
**Page types:** SaaS (checkout/billing flows only).

## Cluster B - Discoverability: SEO, Bots & AI Crawlers, Site Search

Covers items #2, #3, #26, #12. Part 1 §6 already covers the Metadata API, dynamic OG images, JSON-LD, and sitemap/robots baseline - this cluster is everything past that: the icon/manifest matrix, a deliberate per-bot access policy, event-specific rich results, and on-site search.

### 2. Bots Soo Good - good-bot welcome, bad-bot defense
Treat "bots" as three tiers: search engine crawlers (Googlebot, Bingbot), AI answer-engine crawlers, and everything else (scrapers, credential stuffers). Split the AI tier further, since the policy decision differs:
- **Training crawlers** (opt-out only, no citation benefit): `GPTBot`, `ClaudeBot`, `Google-Extended`, `CCBot`, `Applebot-Extended` - a business call on whether Cybercom wants its content used for model training.
- **Answer/citation crawlers** (drive real citation traffic in AI answers): `OAI-SearchBot`, `ChatGPT-User`, `Claude-SearchBot`, `Claude-User`, `PerplexityBot`, `Perplexity-User` - generally worth allowing even if the training tier is blocked.
Declare this explicitly in `app/robots.ts`, and enforce it at the edge with **Arcjet's `detectBot()`** (already installed) rather than hand-rolled user-agent sniffing:
```ts
detectBot({ mode: "LIVE", allow: ["CATEGORY:SEARCH_ENGINE", "CATEGORY:AI", "CATEGORY:PREVIEW"] });
```
This is an **allowlist** - anything not listed is denied - so audit `CATEGORY:AI` periodically, since new scraper bots get misclassified into it to evade blocks. Pair with `isSpoofedBot(decision.results)` before trusting a user-agent claiming to be `GPTBot`/`Googlebot`, or the allowlist becomes a spoofing vector itself. Note `Bytespider` and similar scrapers routinely ignore `Disallow` entirely - robots.txt is advisory, Arcjet is the real enforcement layer. Ship `public/llms.txt` (llmstxt.org format: H1 site name, one-line summary, H2 sections linking key pages) as low-cost, low-certainty upside - adoption is still ~8-10% among top sites and most AI crawlers aren't fetching it yet, so don't treat it as load-bearing. Extend JSON-LD with `FAQPage` (answer engines lift FAQ schema directly into AI Overviews/Perplexity) and `Article` schema (`author`, `datePublished`, `dateModified`) on blog/resource content - answer engines weight structured facts over prose when generating citations.
**Page types:** All.

### 3. SEO Advanced - icon/manifest matrix + OG completeness
Next.js 16 resolves icons via file convention: `app/icon.svg` (dark-mode aware) + `app/icon.png` fallback, `app/apple-icon.png` at **exactly 180×180 with an opaque background** (iOS reads this tag directly and silently ignores off-size files - no error, just a blank home-screen icon), `app/favicon.ico` (legacy/bookmark fallback), and `app/manifest.ts` returning `MetadataRoute.Manifest` (`name`, `short_name`, `start_url`, `display: "standalone"`, `theme_color`, and `icons` - Chrome's installability check hard-requires 192×192 and 512×512 PNGs in that array). A **maskable icon is a separate asset**, not a dual-purpose reuse - artwork confined to the central ~409×409 "safe zone" of a 512×512 canvas, `purpose: "maskable"` as its own array entry distinct from `purpose: "any"`; validate at maskable.app. Gotcha: if both file-convention icons and the Metadata API `icons` field are defined, the Metadata API silently wins - pick one path. Script the whole set from one source logo (a `sharp`-based generator run on brand-asset change) rather than hand-exporting each PNG.
OG completeness beyond title/description/image (already covered): `og:image:width`/`height`/`type` (skips a crawler probe request), `og:image:alt`, `og:url` (canonical, prevents duplicate cards on UTM'd links), `og:site_name`, `twitter:card` set explicitly to `summary_large_image`. For blog/resource pages: `article:published_time`/`modified_time`/`author` via `other: {...}` in `generateMetadata`, since typed Metadata fields don't cover the `article:` namespace. Add a schema-validation CI step (Google Rich Results Test API or a schema.org validator) rather than manual spot-checks, since content edits can silently break the requirement that marked-up price/availability match what's visibly rendered.
**Page types:** All.

### 26. Rich Open Graph schema for events
Two separate things, both required: OG tags for the social-share preview, and `Event` JSON-LD for Google's rich-results carousel (dates/venue/ticket link rendered directly in search). Minimum for Google eligibility: `name`, `startDate` (ISO 8601 **with explicit UTC offset** - never a bare local time, ties to item #29), `location`. For full eligibility add `endDate`, `eventStatus` (`EventScheduled`/`EventCancelled`/`EventPostponed`/`EventRescheduled` - keep it live, stale status is a common validation failure), `eventAttendanceMode` (`Offline`/`Online`/`Mixed`), and `offers` - one `Offer` object per ticket tier (array, not a min/max range; `AggregateOffer` only for a summarized price range) with `price`, `priceCurrency`, `availability`, `url`. **Hard requirement**: if `offers.price` is present in the JSON-LD, it must be visibly rendered on the page - Google's spec penalizes invisible/mismatched pricing as manipulative markup. `og:type` stays `"website"` (Facebook deprecated `og:type: event` years ago) - machine-readable event data belongs in JSON-LD only, with a per-event dynamically generated `opengraph-image.tsx` poster, not the site's generic OG image. Implement as a `buildEventJsonLd(event)` helper colocated with the page's `generateMetadata`, fed the *same* typed event data, so OG tags and JSON-LD can't drift. Multi-session events use `subEvent` or multiple `Event` nodes, not one `Event` with ambiguous dates. Third-party ticketing needs `offers.url`/`price`/`availability` synced via webhook or scheduled poll, never hand-maintained. Validate with Google's Rich Results Test before every event launch.
**Page types:** Event.

### 12. Semantic site search
Don't reach for Algolia by default - it adds recurring cost and a third-party data-egress path that fits poorly with a security company's posture, and its real semantic tier (NeuralSearch) is gated to an enterprise plan anyway. Pick by page type: **Landing/blog/docs** → **Pagefind** - a Rust-based indexer that runs as a post-`next build` step against rendered HTML, ships the index as static files (`/_pagefind/`) served from the same CDN, zero runtime backend or API key. Keyword + fuzzy only (no true vector search), which is fine for a curated content set but weak on long, easily-misspelled queries; it also can't index gated/auth-only content since it walks build-time HTML, so it's not a fit for SaaS/Internal. **SaaS in-app search** → **Orama** (in-memory, TypeScript, runs client-side or at the edge, supports bring-your-own-embeddings vector search, sub-millisecond since there's no network round trip) or **Meilisearch** (self-host free / Cloud ~$30/mo, hybrid keyword+vector built into every plan) if facets/relevance at larger content volume matter more than avoiding a hosted service. **Internal tools** → DIY embeddings on the existing Postgres via `pgvector`/Supabase only if semantic recall over something like incident reports is genuinely core to the workflow; otherwise self-hosted Meilisearch is simpler. Any embeddings-based approach needs a publish-time re-index trigger or search goes stale. Hybrid (keyword+vector) generally beats pure-vector for site search - prefer Meilisearch/Orama's built-in hybrid mode over hand-rolling pure-vector matching.
**Page types:** Landing (Pagefind) / SaaS (Orama or Meilisearch) / Internal (Meilisearch, or DIY embeddings if justified) / Event (Pagefind, if a multi-event directory exists).

## Cluster C - Performance, Loading, Errors & Layout Integrity

Covers items #5, #7, #9, #11, #19, #27, #30, #52, #55. Next.js App Router's `loading.tsx`/`error.tsx`/`not-found.tsx` conventions only cover three states - everything else here is either CSS discipline, a React 19 hook, or a proxy-layer workaround for the status codes Next.js doesn't natively route.

### 5. Loading Screen
Reserve a full-route loading screen for route segments doing genuinely slow first-paint work (auth check + heavy data fetch on a SaaS/Internal dashboard entry, or an asset-heavy 3D hero) - not as a branded intro splash gating content that hasn't even been requested yet, which is a pure UX tax and a classic "vibe-coded" tell. Implement via the App Router `loading.tsx` file convention, which Next.js wraps around the route's `page.tsx` in a Suspense boundary automatically. Mirror the final layout's chrome (header/nav present, content area as skeleton per #27) rather than a centered spinner, so there's no flash-to-different-layout. If the route resolves under ~300ms the boundary won't even paint - don't add an artificial minimum display time.
**Page types:** Landing (asset-heavy hero only), Internal (dashboard cold-start).

### 11. The "Loading" state
Distinct from #5: every element that triggers async work (button, form, filter, toggle) needs its own local pending state, not a global spinner decoupled from what was actually clicked. Use `useTransition`'s `isPending` for client-triggered work and `useFormStatus()`/`useActionState()` for Server-Action-backed forms - disable the trigger, swap label/spinner glyph, set `aria-busy="true"` on the affected region. At the route level, prefer granular `<Suspense fallback={...}>` around individual slow Server Components over one route-level `loading.tsx` - this streams fast parts of the page (nav, hero) immediately while slow parts (a table, an AI response) arrive later. Wrap repeated fetches in `React.cache()` so parallel Server Components sharing data don't re-issue the same request.
**Page types:** All.

### 27. Skeleton state placeholders
Skeletons beat spinners for perceived performance only when dimensions match the *actual resolved* content exactly - a mismatched skeleton just delays the CLS problem it was meant to prevent instead of preventing it. Build a `<Skeleton>` primitive using `animate-pulse` (`tailwindcss-animate`, already installed) on brand-token gray/steel shades (not generic gray, to stay on-brand for Armory style), colocated with each feature's real component so the two can't silently drift apart. Pair granular Suspense boundaries (per #11) around individual async Server Components (stats card, table, chart) with per-boundary skeleton fallbacks. Skip skeletons for anything resolving under ~1s - a flashing skeleton reads as noisier than no state; past ~3s, add a progress indicator instead of an indefinite pulse.
**Page types:** All (heaviest use on SaaS/Internal data views).

### 19. Optimistic UI updates
React 19's `useOptimistic` is the 2026 default over hand-rolled state juggling: `const [optimisticState, addOptimistic] = useOptimistic(state, reducerFn)`, called synchronously inside the event handler *before* awaiting the Server Action - React shows the optimistic value immediately and reconciles (or reverts) once the async call settles. Use it for local, component-scoped echoes (toggling, adding a comment, incrementing a counter). For optimism against a shared cache/data graph that multiple views read (a list mutation affecting several components), pair it with - or defer to - the mutation library's cache-level optimism (TanStack Query's `onMutate`/`onError` rollback) so every consumer of that cache key stays consistent; `useOptimistic` alone doesn't propagate across unrelated components. Always design a visible revert path (toast/shake) for the failure branch - a silent revert erodes trust worse than no optimism at all.
**Page types:** SaaS, Internal, Event.

### 52. Instant local-first architecture
An architecture decision, not a page-level tweak - scope explicitly to SaaS/Internal tooling, never the marketing site. 2026 landscape: **PouchDB is legacy** (unmaintained since 2024, don't start new work on it). **RxDB** is the mature, batteries-included default (reactive queries over IndexedDB/SQLite/OPFS, multi-tab sync, a replication plugin for background push/pull, `encryption-web-crypto` for at-rest field encryption). **Dexie.js** is the lighter alternative when only a fast reactive IndexedDB wrapper is needed, without RxDB's schema-validation/replication machinery. Two newer options worth evaluating specifically because they solve permissions, which matters for a security-focused product: **Zero** (from the Replicache team) syncs only the rows a given user is authorized to see, rather than requiring the client to filter a full local replica; **ElectricSQL** is the right call if the backend is already Postgres and sync should run on local `PGlite`. **TanStack DB** is promising but still maturing - evaluate, don't commit production work to it yet. Pattern: RxDB/Zero/etc. collections are the source of truth in the browser; UI reads/writes hit local storage only (instant, no network wait); a background replication layer pushes/pulls deltas (default conflict strategy is last-write-wins - override with a custom conflict handler for merge-sensitive fields). Because Cybercom is security-positioned: anything cached locally is plaintext in IndexedDB by default and readable via devtools on a shared/compromised machine - treat "what data is allowed to live in local-first storage at all" as a security review item, not just a perf one, and encrypt sensitive collections. This is additive to #19 (optimistic UX) and #36 (offline banners, Cluster G) - not a replacement for either.
**Page types:** SaaS, Internal.

### 9. Missing width/height (CLS), alt text, .webp/.avif only
`next.config.ts` restricting `images.formats` to AVIF/WebP only governs images served through `next/image` - it does not touch raw `<img>` tags, CSS `background-image`, or third-party embeds, so those still need manually-exported `.avif`/`.webp` source files (no raw `.png`/`.jpg` reachable by URL in `public/`). Always use `next/image` over a bare `<img>` - it enforces `width`/`height` (or `fill` with a sized, `position: relative` parent) at the type level, which is what actually prevents CLS. Add `priority`/`fetchPriority="high"` on the single LCP image only (Google's own benchmarks show ~2.6s → ~1.9s LCP from this alone) - applying it to more than one image defeats the prioritization. For non-`next/image` cases (icon sprites, embeds, video posters), reserve space with `aspect-ratio` as a fallback so the box exists before the asset loads. Alt text: decorative images get `alt=""` (not omitted - omitted alt is worse, screen readers announce the filename instead), meaningful images get descriptive alt written for a screen-reader user first, never keyword-stuffed. Lint-enforce with `eslint-plugin-jsx-a11y`'s `alt-text` rule in CI rather than relying on review to catch it.
**Page types:** All.

### 55. Blank space when scrolled up (the "vibe-coded" layout bug)
Almost always one of four diagnosable root causes - check in this order before reaching for a fix:
1. **iOS Safari elastic overscroll ("rubber-banding")** reveals whatever's beyond the content edge - if `<html>` and `<body>` have different (or no) background colors, overscrolling past the top/bottom shows raw unstyled space. Fix: match `background-color` on both `html` and `body`, and set `overscroll-behavior-y: contain` (or `none`) on `body` to contain the bounce (note: `none` also disables pull-to-refresh - usually fine, confirm with the client).
2. **`100vh` vs. `100dvh` mismatch**: `100vh` on mobile is calculated against the *largest* possible viewport (chrome retracted) - taller than what's visible on initial load with the address bar showing, producing a blank strip below the fold that disappears once the user scrolls. Use `100svh` (smallest viewport) for hero/full-bleed sections; never animate a height property between a fixed value and a `dvh`/`svh` value (constant recalculation causes visible jitter) - animate `transform`/`scale` instead.
3. **Sticky/fixed header offset drift**: anchor-link or programmatic scroll landing a section edge exactly under a `position: sticky`/`fixed` header. Fix with `scroll-margin-top` on target sections (or `scroll-padding-top` on the scroll container), not manual negative-margin offsets that break the moment header height changes responsively.
4. **Scroll-anchoring misfires**: the browser's default scroll-anchoring (`overflow-anchor: auto`) tries to preserve visual position when off-screen content resizes, which can fight custom scroll-jacking/GSAP-driven sections (relevant given brutalist layouts favor pinned/scrubbed sections) and produce visible micro-jumps. Set `overflow-anchor: none` explicitly on any container with JS-driven scroll or frequently-resizing injected content (toasts, chat widgets).
Test on a real iOS Safari device after shipping any new full-bleed/pinned section - Chrome DevTools' device toolbar does not simulate elastic overscroll, so this bug class reliably survives desktop review and ships anyway.
**Page types:** All.

### 7 & 30. Custom error pages (400–504) and static 5xx fallbacks
Next.js App Router natively special-cases exactly two states by file convention: **404** (`not-found.tsx`, triggered by `notFound()` or an unmatched route) and **uncaught render-time exceptions** (`error.tsx` per-segment boundary; `global-error.tsx` only if the root layout itself throws, and must be a fully standalone `<html>`/`<body>` with zero dependency on shared providers, since those may be what crashed). **There is no file convention for 401/403/410/429 or any 5xx** - those either originate outside the React render pipeline entirely, or need to be constructed by hand:
- **401/403/429/400** typically originate in `src/proxy.ts` (Next 16's renamed `middleware.ts`) - e.g. Arcjet's `decision.isDenied()` branching on `isBot()` (403) or `isRateLimit()` (429) returns a raw `Response`/`NextResponse` object, not a React-rendered page. For page-level UX (an authenticated-but-unauthorized user), Next.js 15+ added experimental `forbidden()`/`unauthorized()` functions paired with `app/forbidden.tsx`/`app/unauthorized.tsx` boundaries - use these instead of a manual redirect where available.
- **410 Gone** has no built-in helper (`notFound()` always yields 404) - a deliberately-retired route needs its own `page.tsx`/Route Handler explicitly returning/rendering with `status: 410`.
- **502/503/504, and 500s before Node is even up**, are the hosting platform reporting Next.js is unreachable/timed out - `error.tsx` never runs here, since there's no Node process to run it. On Vercel, drop status-code-named static HTML files directly in `public/` (`public/500.html`, `502.html`, etc. - undefined codes fall back to `500.html`, so one well-designed 500 page covers the whole platform-outage class at minimum). These files must be fully self-contained: inline `<style>` only, no Tailwind build, no `next/font`, no external requests - hardcode brand tokens as literal CSS values, since nothing behind them can be trusted to load. Keep this file manually in sync with the Armory visual language whenever core design tokens change; it sits outside the normal build pipeline so nothing will flag drift automatically.
To keep one coherent Armory look across three completely different code paths (React components, a `proxy.ts` response body, static HTML with no build step), don't try to share a literal React component across them - maintain one canonical error-shell markup (big monospace status numeral, terse copy, scanline/grid background, brand colors as literal CSS custom properties) and re-implement it three times from that single source: React components for `not-found.tsx`/`error.tsx`/`global-error.tsx`/`forbidden.tsx`/`unauthorized.tsx`; a plain-string template helper (`lib/error-shell.ts`, importable since `proxy.ts` runs on the Node runtime in Next 16, not Edge) for the 401/403/429/400/410 responses constructed by hand; and the static `public/*.html` files for platform-level 5xx, which can't import anything at request time and must stay copy-pasted. Error pages should be a deliberate on-brand illustration opportunity, not generic boilerplate text - this repo's existing `not-found.tsx`/`error.tsx` are the baseline to upgrade from.
**Page types:** All.

## Cluster D - Motion, Sound & Sensory Polish

Covers items #15, #16, #20, #23, #37, #39, #40, #53, #54.

**The CSP finding that governs this entire cluster:** this project's nonce-based `style-src` blocks anything that mutates the HTML `style` **attribute** as a whole - inline `style=""` markup, `setAttribute('style', …)`, `.style.cssText = …` - because CSP nonces only attach to `<style>`/`<link>` elements (there's no attribute-nonce mechanism), and `'unsafe-inline'` is ignored the instant a nonce is present. It does **not** block direct CSSOM property writes (`el.style.transform = …`, one property at a time) or the Web Animations API (`el.animate()`), since neither touches the attribute-mutation path CSP hooks into. That's why GSAP (writes per-property via CSSOM) and WAAPI-driven effects work fine under this policy, while **Framer Motion is confirmed broken under nonce CSPs** (`framer/motion#1727`, closed *wontfix*, no nonce support planned) - it batches per-frame writes to the `style` attribute as a whole. Treat Framer Motion as unusable for anything in this cluster until that's fixed upstream or the CSP is loosened; every recommendation below routes around it. Keep motion mechanical/industrial (linear or stepped easing, sharp starts/stops) to match the Armory direction, not bouncy/playful.

### 15. Scroll-driven micro-animations
Native CSS `animation-timeline: view()`/`scroll()` is the default now - pure CSS, no JS, CSP-nonce-safe by construction (it's not writing to a `style` attribute at all), and runs on the compositor thread. Support (mid-2026): Chrome/Edge 115+, Firefox 132+, Safari 18+, ~84% global. Pattern: write a normal `@keyframes`, then `view-timeline-name: --reveal` on the container + `animation-timeline: --reveal; animation-range: entry 0% cover 40%;` on the element; for viewport-relative scroll (progress bars), use `animation-timeline: scroll(root block)` directly. Gate with `@supports (animation-timeline: scroll())` and provide a static fallback for the remaining ~16%; override to `animation-timeline: none` under `prefers-reduced-motion`. No JS hook exists for side effects mid-scroll - pair with `IntersectionObserver` if one is needed.
**Page types:** All.

### 20. Scroll-driven timeline triggers (GSAP)
Reach for GSAP ScrollTrigger only when native scroll-timelines (#15) can't express it - pinning, scrubbed multi-step sequences, horizontal-scroll set pieces, cross-element choreography. Free for commercial use since GSAP 3.13; use the official `@gsap/react` `useGSAP()` hook (automatic cleanup, critical under Strict Mode/App Router remounts) rather than raw `useEffect`. Register once at app root; tear down (`ScrollTrigger.getAll().forEach(t => t.kill())`) on route change to avoid instance leaks across client navigations. GSAP's `CSSPlugin` writes each animated value via direct CSSOM property assignment (`element.style.transform =`), not by replacing the whole attribute - this path is not intercepted by `style-src`, and no GitHub issue or forum thread reports CSP breakage for GSAP specifically. GSAP publishes no formal CSP-compliance statement though, so smoke-test against this project's actual CSP header (watch DevTools console for `Refused to apply inline style`) before shipping any new GSAP-driven section - per CLAUDE.md's standing warning, verify animation in a real browser, not just that it compiles. Scrub-linked pinning is expensive on low-end mobile - throttle or disable under `prefers-reduced-motion`.
**Page types:** Landing, Event.

### 54. Perfect dark/light mode transitions (View Transitions API)
Circular wave clip-path expanding from the exact cursor coordinate that clicked the theme toggle:
```js
function toggleTheme(e, setTheme, next) {
  const x = e.clientX, y = e.clientY;
  const r = Math.hypot(Math.max(x, innerWidth - x), Math.max(y, innerHeight - y));
  if (!document.startViewTransition) return setTheme(next);
  const t = document.startViewTransition(() => setTheme(next)); // sync theme flip inside the callback
  t.ready.then(() =>
    document.documentElement.animate(
      { clipPath: [`circle(0px at ${x}px ${y}px)`, `circle(${r}px at ${x}px ${y}px)`] },
      { duration: 500, easing: "ease-in", pseudoElement: "::view-transition-new(root)" }
    )
  );
}
```
Call `setTheme` (via `next-themes`, already installed) synchronously inside the `startViewTransition` callback so the DOM snapshot captures the correct before/after state. This is CSP-clean: `.animate()` operates on `::view-transition-*` pseudo-elements via WAAPI, never the `style` HTML attribute - same exception class as GSAP's CSSOM writes, no CSP change required. Support (2026): same-document transitions (what a theme toggle needs) - Chrome/Edge 111+, Safari 18+, Firefox 133+, safe as the primary path now; cross-document/MPA transitions have weaker support but are irrelevant here. Disable the default root cross-fade (`::view-transition-image-pair(root) { animation: none; mix-blend-mode: normal }`) or it fights the clip-path; guard `prefers-reduced-motion: reduce` with an instant swap; duplicate `view-transition-name`s elsewhere on the page silently kill the whole transition.
**Page types:** All.

### 16. Sound UI
The design-system decision layer sitting above #53 (which handles synthesis) - which interactions get audio at all: toggle, submit, nav open/close, error/success. Ship as an explicit opt-in, default OFF, with a persistent mute toggle remembered in `localStorage` - most users have sound muted by habit, and unexpected audio reads as a bug or an ad, which is a real trust risk on a security-brand site. A single confirmation chime on checkout/CTA success is the safe default for Landing; ambient/embedded audio is not.
**Page types:** SaaS, Landing (sparingly).

### 53. Audio-synthesized UI interactions (Web Audio API)
Don't ship `.mp3` files - synthesize on the fly with a raw `OscillatorNode` → `GainNode` envelope, which is lighter than Tone.js (~200KB) for one-shot UI blips (reserve Tone.js only for actual musical scheduling/transport):
```js
function playTone(freq, velocity = 1) {
  const osc = ctx.createOscillator(), gain = ctx.createGain();
  osc.type = "triangle"; // 'square' for a harder, mechanical Armory click
  osc.frequency.setValueAtTime(freq * (0.98 + velocity * 0.04), ctx.currentTime);
  gain.gain.setValueAtTime(0.0001, ctx.currentTime);
  gain.gain.exponentialRampToValueAtTime(0.15 * velocity, ctx.currentTime + 0.01);
  gain.gain.exponentialRampToValueAtTime(0.0001, ctx.currentTime + 0.12);
  osc.connect(gain).connect(ctx.destination);
  osc.start(); osc.stop(ctx.currentTime + 0.15);
}
```
Derive `velocity` from pointer speed or scroll delta/time; quantize the frequency to a fixed pentatonic/brand scale array so any velocity-derived pitch still sounds harmonized rather than random. Derive the whole UI sound family - click, hover, success, error, toggle - from **one shared base frequency, oscillator type, and envelope shape**, varying only frequency ratio and duration per event, so the kit sounds coherent instead of like disconnected stock effects; square/sawtooth oscillators with tight envelopes (short attack, fast decay) read as "terminal/industrial" for Cybercom's brand, not sine-wave "soft app" chimes. `AudioContext` must be created/resumed on a user gesture (browser autoplay policy - unrelated to CSP, which has no jurisdiction over Web Audio at all) - lazily instantiate on first interaction. iOS Safari suspends `AudioContext` on backgrounding - call `.resume()` on visibility change. Explicitly `.disconnect()` nodes after `stop()` to avoid graph/GC churn on rapid repeated interactions.
**Page types:** SaaS, Landing.

### 37. Micro-typography & layout polishing
A discipline checklist to run per component, not a library: optical alignment over mathematical centering (icons/glyphs often need a 1-2px nudge to *look* centered); `text-wrap: balance` on headlines / `text-wrap: pretty` on body copy (both broadly supported by mid-2026, prevents orphan words and ragged last-lines - `balance` has a browser-imposed line-count cap, verify it still balances at your longest real heading); `font-variant-numeric: tabular-nums` on any stat counter/dashboard/table so digits don't jitter-shift width as they change; hanging punctuation on large pull-quotes; negative `letter-spacing` tracking on large display headlines; variable-font `font-optical-sizing: auto`. Centralize as reusable Tailwind v4 `@theme` utility classes rather than one-off inline fixes, consistent with Part 1 §5's token-layering approach.
**Page types:** All.

### 39. Smart asset strategy - dynamic SVG color syncing
Inline SVGs as React components directly in JSX (not `<img src>` - a referenced SVG file can't see page CSS) with `fill`/`stroke` bound to `currentColor` or a CSS variable (`var(--icon-color)`) defined in `@theme` and flipped by `next-themes`' `data-theme`/class attribute - a single token change recolors every icon/illustration sitewide with zero duplicate light/dark asset exports. Strip hardcoded fills at build time (SVGR `svgProps: { fill: 'currentColor' }`). For decorative brand artwork too complex to inline cleanly, use `mask-image` with a solid `background-color` set to the token - the asset becomes a shape mask, color stays a live CSS variable. `<img src="icon.svg">` and CSS `background-image: url(...)` are opaque to page custom properties - use the mask technique for those cases instead of trying to force `currentColor` through them. Avoids the classic failure mode of shipping two static PNG exports (light/dark) that drift out of sync on the next brand tweak.
**Page types:** All.

### 40. Intentional focus states
WCAG 2.2's focus-appearance expectation sets concrete minimums by 2026: an indicator area at least a 2px-thick perimeter around the focused element, with **≥3:1 contrast** against the adjacent color in both focused and unfocused states. Implement globally via `:focus-visible` only (never bare `:focus`, so mouse clicks stay clean and only keyboard/AT nav shows the ring):
```css
:focus-visible { outline: 2px solid var(--color-focus-ring); outline-offset: 2px; }
```
token-driven per theme, consumed by shadcn/ui's default `focus-visible:ring-*` classes for consistency. For components sitting on unpredictable backgrounds (cards over photos, dark-mode-variable surfaces), use the **double-outline technique** - two concentric outlines, one light one dark, with ≥9:1 contrast between them - so at least one ring stays visible regardless of what's underneath. Design the ring as an on-brand element (a hard-edged bracket/reticle shape) rather than default browser blue - a place brutalist styling can genuinely outperform the default. Test with `@storybook/addon-a11y` plus visual regression capturing `:focus-visible` states explicitly, since `axe-core` catches missing focus styles but not insufficient ring contrast.
**Page types:** All.

### 23. Dark mode contrast guards
A CI/design-review gate, not a runtime feature: every semantic color token pair (`--color-text-primary` on `--color-surface`, both light and dark values) must independently clear WCAG AA (4.5:1 body text, 3:1 large text/UI components) - dark mode is not "invert and ship," since desaturated/muted tones that pass in light mode frequently fail once background luminance flips. Author tokens in OKLCH (Tailwind v4 native, perceptually linear lightness) and clamp floors/ceilings (e.g. `oklch(0.15 …)` instead of true black) instead of pure `#000`/`#FFF`. Enforce with a CI script running `culori` or `colorjs.io` (both ship the same WCAG 2.1 + APCA `Lc` engine Tailwind v4 uses internally) over every token pair per theme, asserting a hard WCAG floor (`≥ 4.5:1`) and optionally a tighter APCA target (`Lc ≥ 60` body / `≥ 75` small text) as an advisory layer - APCA is polarity-aware (light-on-dark and dark-on-light need independent checks) and still a draft pre-WCAG-3 spec, so treat it as a tightening layer, not the hard gate. Fail the build on regression, matching the "gate in CI" pattern Part 1 already uses for Lighthouse/Knip.
**Page types:** All.

### 51. Full keyboard-driven Vim mode

### 32. Keyboard-only speedrun mode

### 18. Instant content previews
Next.js `<Link>` already prefetches route RSC payloads on viewport intersection by default - layer a hover-triggered `@radix-ui/react-hover-card` (same Radix family already installed) with an `openDelay` ~300–500ms to avoid firing on fast mouse-throws, showing OG metadata or a purpose-built lightweight preview fragment. ### 46. Zero-delay "ghost" previews
Derive the preview purely from in-memory draft state (a `useReducer` or Zod-validated object - reuse the *same* Zod schema that validates the eventual Publish mutation) so toggling a switch never round-trips to the server. For email/workflow previews, render the actual production template component (e.g. the same React Email component used for real sends) fed the draft data - preview should equal production render, not a simulated approximation. Give "Publish" and "Preview" one shared Server Action with a `dryRun` flag so they can never drift. A preview must never cause a side effect - no real sends, no real writes, enforced by the dry-run flag, not by convention. Debounce expensive derivations (revenue projections) ~150–300ms even though the goal is "zero delay," to avoid jank on rapid slider drags; virtualize rendering for large schema diffs.
**Page types:** SaaS, Internal.

### 8. Double-click prevention, form state persistence, proper `<form>` semantics
Use a real `<form action={serverAction}>` with `useActionState(action, initialState)`, and `useFormStatus()` read inside a child `<SubmitButton>` component (`pending` is only available in a *descendant* of the form, not the form component itself) to set `disabled={pending}` - this is React 19's built-in double-submit guard, no manual `isSubmitting` state required. Client-side `disabled` alone isn't sufficient - also generate a `crypto.randomUUID()` idempotency key in a hidden input on mount and dedupe on it server-side, covering retries, multi-tab submits, and Enter-key races. For drafts, debounce-write form values to `sessionStorage` (survives refresh) or `localStorage` + a stable form id for cross-session persistence, rehydrate via `defaultValue`, clear on the action's success branch. Prefer uncontrolled inputs + native `FormData` (which Server Actions read directly) over React Hook Form for simple forms - RHF has no official persistence plugin, and simple forms don't need the extra dependency. Use real `<label htmlFor>`, `required`, and correct `type`/`autocomplete` so native validation and password managers actually function - never build div-based pseudo-forms. Never persist sensitive fields (passwords, payment info) to storage on shared/kiosk machines.
**Page types:** All.

### 22. Lead-capture smart autofill
Use exact WHATWG `autocomplete` tokens (`name`, `email`, `tel`, `organization`, `street-address`/`address-line1`, `address-level2`, `postal-code`, `country`) - browser/password-manager autofill keys off the token string itself, not just `type`. For OTP verification, `autocomplete="one-time-code"` alone triggers Safari/iOS SMS-suggest autofill with zero JS; layer the **WebOTP API** (`navigator.credentials.get({ otp: { transport: ['sms'] } })`, feature-detected via `'OTPCredential' in window`) for Chrome/Android auto-submit - Chrome also supports cross-device (desktop) OTP retrieval via a shared Google account since Chrome 93. The SMS body must follow the bound-origin format (`@yourdomain.com #123456`) and requires HTTPS. Pair with `inputmode="numeric" pattern="[0-9]*"` for the OTP field's mobile keyboard, and prefill hidden UTM fields from the query string for attribution. Abort the OTP listener (`AbortController`) on unmount/route change to avoid a dangling permission prompt; WebOTP is progressive enhancement only (Safari has no support at all, `autocomplete="one-time-code"` is the universal baseline); never auto-submit purely because a field was autofilled - keep it editable, autofill can be stale or wrong (work vs. personal email).
**Page types:** Landing, Event.

### 31. AI speech bot
Three tiers, pick by budget - figures below verified against vendor pricing pages as of 2026-07-31, re-check before quoting in a client budget. **Free**: the browser's native Web Speech API (`SpeechRecognition` + `SpeechSynthesis`) - zero backend, but robotic voice quality and inconsistent Firefox support (Chrome/Edge are the reliable targets); ship it as a progressive enhancement, not the only input method. **Vendor-orchestrated (fastest to production quality)**: **Vapi** (Build plan $0.05/min hosting + model cost pass-through, 10 free concurrent calls then $10/mo per line; HIPAA add-on $2,000/mo, zero-data-retention add-on $1,000/mo - advertises <500ms average latency) or **Retell AI** ($0.07–0.31/min all-in, itemized ~$0.055/min voice infra + $0.015–0.04/min TTS + $0.003–0.16/min LLM, no platform fee, 20 free concurrent calls, +$0.01/min for PII removal) - both give a managed STT→LLM→TTS chain plus a dashboard, and are the pragmatic middle tier before building the realtime stack by hand. **Full custom (lowest latency)**: **OpenAI's Realtime API** (`gpt-realtime`, token-priced not per-minute - audio input $32/1M tok, audio output $64/1M tok, cached input $0.40/1M tok, ≈$0.10–0.15/min blended) does native speech-to-speech over WebRTC, no separate STT→LLM→TTS hop, 300–800ms latency; **ElevenLabs Conversational AI** (credit-metered: Free 10k/mo, Starter $6→30k, Creator $11→121k, Pro $99→600k) gives the best default voice quality/cloning, fine for non-time-critical flows. The Vercel AI SDK is at v7 (`ai@7.x` on npm) and is a reasonable unified tool-calling layer behind whichever vendor is chosen, but realtime audio transport still goes through each vendor's own SDK, not the AI SDK itself - it's not currently an installed dependency in this repo. Either realtime API key must be proxied server-side (a Route Handler issuing short-lived ephemeral tokens) - never in the client bundle, same rule as Part 1 §3's "proxy all third-party secret-key calls." Rate-limit the endpoint with Arcjet (already installed) - a public voice bot is a fresh abuse *and cost* surface (prompt injection, scripted call-flooding burns real per-minute spend). Ground all answers in a real knowledge base (RAG over actual site/docs content) and refuse out-of-scope security claims - hallucination is a real liability for a security brand. Never auto-request mic permission on load; disclose retention in the privacy policy; always ship a text fallback.
**MVP cut:** Web Speech API only - mic button transcribes to text, feeds an existing text-chat backend, reads the reply back with `SpeechSynthesis`. Zero new vendor cost.
**Page types:** Landing, SaaS.

### 41. Dynamic video interface (the AI concierge)
**Cheap-and-real**: pre-render a small library of avatar video clips (welcome message, top-5 FAQ answers) via **HeyGen** (Creator $29/mo–600 credits, Pro $49/mo–1,000 credits, Business $149/mo–1,500 credits; standard Avatar III generation = 3 credits/min) or the Higgsfield MCP connector already available in this session - then just switch between static clips on user action, served as a normal `<video>` element. **Page types:** Landing, Event.

### 43. Instant AI calendar matchmaker
Two ingestion paths. **ICS paste (no OAuth)**: accept a public `.ics`/`webcal://` URL, fetch and parse with `node-ical` or `ical.js` - zero consent friction, ships fastest. **Google Calendar connect**: OAuth via Auth.js/better-auth's Google provider requesting only the narrow `calendar.freebusy` scope (not full `calendar.readonly`), then call `freebusy.query` for the event's date range (capped at ~3 months). Critical honesty point: **the conflict-resolution math must be deterministic code, not an LLM** - interval scheduling / greedy slot allocation weighted by a stated interest score is a solved, testable algorithm; LLMs are unreliable at exact interval arithmetic and a hallucinated "non-conflicting" slot that actually overlaps is a real failure mode. Use the LLM only for the natural-language layer - turning "I care more about the security talks than the networking mixer" into a priority-weight input to the deterministic scheduler. Emit the result as a downloadable `.ics` file (recommended) or a direct `events.insert` batch call if write-scope is added later. Requesting write scopes (`calendar.events`) past a small user cap triggers Google's OAuth app-verification/CASA review - real overhead for a small team; sticking to `freebusy` (read) + generated `.ics` avoids that review entirely. Never persist a visitor's calendar data past the session without explicit consent (DPDPA/GDPR, Part 1 §7).
**MVP cut:** ICS-paste only, deterministic greedy scheduler by track/tag, output a downloadable `.ics` + "add to calendar" webcal link - ships in a sprint, no Google verification process needed.
**Page types:** Event.

### 49. Predictive smart actions
Honest framing: this is scheduled pre-computation plus a simple usage heuristic, not a predictive ML model - and that's the correct, cheaper, more reliable choice. Log action events (report type, timestamp, user) through the already-installed PostHog SDK or a first-party events table; a rolling per-weekday histogram flags an action "predictable" if it recurs in ≥3 of the last 4 occurrences within a time window - a plain threshold rule, not a time-series model, and auditable by a two-person team. A scheduled job (**Vercel Cron** - Hobby only guarantees firing within the hour, Pro/Enterprise guarantee the minute, which matters for a "5 minutes before 9am" prediction; or **Inngest**/**Trigger.dev** for retryable scheduled functions) runs ~5 minutes ahead of the predicted time, computes and caches the result (Vercel KV/Redis, or Next.js `unstable_cache`/`revalidateTag` on a time-bound tag). On login, read the cache - instant toast: "We already compiled your Monday report." Cron does not run in local dev at all - trigger manually or via a local scheduler when testing. Show a "last updated" timestamp so a stale pre-computed report is never mistaken for live data. Cap precompute to cheap-to-generate reports only, and expire/regenerate if underlying data changed between precompute and click.
**MVP cut:** no cron, no pre-5-minute scheduling - on login, check if the action/time matches the ≥3-of-4-week pattern directly against the existing events table, pre-warm the cache asynchronously right after login, toast on the *next* visit. Removes the scheduling infrastructure entirely for v1.
**Page types:** SaaS, Internal.

### 13. Dynamic UI personalization
Use PostHog feature-flag payloads (already installed) keyed on person properties or cohort - e.g., a different hero headline for a visitor tagged as an enterprise-buyer cohort vs. an individual developer, segmented by UTM/referrer or a self-reported role from a short gate/quiz. Evaluate flags **server-side** (via `posthog-node`, keyed on the `distinct_id` cookie, using PostHog's local-evaluation/bootstrap mode to avoid an added network hop) for above-the-fold content - client-side evaluation causes a flash of unpersonalized content on load. This directly collides with the CSP/static-generation trade-off already flagged in Part 1 §3: server-evaluated personalization forces dynamic rendering on that route, same as nonce-CSP does - treat it as the same trade-off, not a new one. Googlebot must see a stable default variant (detect and bypass personalization for crawlers) or SEO content becomes inconsistent. More variants than the team can maintain content for is the real failure mode - two or three durable segments beat ten that go stale in a month; don't build this for low-traffic pages, since you need real volume to know a variant is winning rather than reading noise.
**MVP cut:** 2–3 hero/CTA variants keyed only by UTM/referrer (no login or behavioral tracking required), evaluated server-side with PostHog bootstrap to avoid flicker - doubles as reusable A/B-test infra.
**Page types:** Landing, SaaS.

### 45. Dynamic UI layout morphing
Be explicit with clients about what this actually is: **not** a dashboard silently rewriting its own DOM based on an autonomous model - that's not how this gets built in production in 2026, and a genuinely autonomous layout AI would erode user trust anyway (surprise UI changes break muscle memory and read as broken, not smart). The real, buildable version is a frequency-weighted heuristic, not a trained model: fire widget-level interaction events (view time, click-through, dwell) to PostHog with a `widget_id`, aggregate a per-user "attention score" per widget over a trailing 7–14 day rolling window (piggyback on the #49 cron pattern), store the resulting order in a `layout_weights` jsonb column on the user record. Surface a **dismissible, opt-in suggestion** - "You use Server Logs 5× more than Billing - reorder your dashboard?" - with one-click apply, never an automatic silent rearrangement. Keep a hard floor so compliance-relevant widgets (billing) are never fully hidden regardless of score, and hysteresis so it only shifts after a multi-session stable trend. Cold start: new users have no signal, so ship the sensible default order and only start suggesting after N sessions. Reordering visual position without reordering the underlying DOM/ARIA structure can break screen-reader navigation - keep it within a stable landmark structure.
**MVP cut:** no auto-morphing at all - ship a manual "pin to top" per widget with persisted order, using the same events pipeline to power a confirm-before-apply nudge. Keeps a human in the loop and sidesteps the trust/accessibility risk of automatic layout changes.
**Page types:** SaaS, Internal.

## Cluster G - Real-Time Collaboration, Sync & Offline

Covers items #25, #33, #36, #47, #48, #50. All six share one truth: "real-time" is a spectrum from "add an SSE endpoint" (hours) to "stand up a CRDT sync backend" (weeks) - pick the cheapest tier that satisfies the actual use case before reaching for the fancy one.

### 50. CRDT-powered peer-to-peer document syncing
Conflict-free collaborative editing (Google-Docs/Notion-style) where offline edits merge automatically on reconnect, no manual conflict resolution. **Library**: Yjs is the 2026 production default (~920K weekly downloads, fastest of the CRDT libraries, largest ecosystem of editor bindings - Tiptap, ProseMirror, Monaco, Lexical). Pick Automerge instead only for its Git-like change-history/versioning model specifically - Automerge 2.0 closed most of its old performance gap but still trails Yjs's raw throughput. **Backend/transport**: don't write a custom WebSocket relay. Cheapest: **Liveblocks** (managed rooms + Yjs storage + presence + comments, React-first components, pay-per-room - ships fastest, pricing gets unpredictable at high room counts). Full-control/self-hosted: **`@hocuspocus/server`** (self-hosted Yjs websocket server, open source, actively maintained, you own infra). **Correction - do not reach for PartyKit here**: despite older write-ups recommending it, both `partykit` and `y-partykit` on npm have shipped zero releases since May/June 2025 - effectively dormant since Cloudflare's April 2024 acquisition, superseded by Cloudflare's own actively-released **Agents SDK** on Durable Objects, which is the current edge-native option if Hocuspocus's ops burden isn't wanted. Verify npm publish dates before trusting any "use PartyKit" recommendation, including older drafts of this doc. This is a real feature, not a checkbox - budget for it only when a genuine multi-editor document exists (shared incident notes, a collaborative proposal builder); bolting Yjs onto a single-editor form is pure overhead.
**Complexity tier:** high (new infra + new failure modes: room lifecycle, auth-per-room, storage costs).
**Page types:** SaaS, Internal.

### 48. Collaborative cursor multi-presence (the "Figma effect")
Live cursors, selection highlights, small avatars showing what teammates are looking at right now - pure perceived-value polish, no data merge required, and much cheaper than #50. If Liveblocks is already paid for #50, its `useOthers`/`useMyPresence` hooks give cursor broadcast in a few lines - the pragmatic default when #50 is already in the stack. If #50 isn't in play (or the same transport needs to cover #25's public event-page broadcast too), standardize on **Ably** instead: core Pub/Sub channels for generic broadcast, plus **Ably Spaces** (`@ably/spaces`, a purpose-built presence SDK layered on the core client) for this item specifically - cursor-position tracking, member avatars/online-status, and a `locations` API for "which row/component a teammate currently has focus on," the closest out-of-the-box match to the spec; layer text-selection syncing as a custom Pub/Sub event (`{selectionRange, docId, userId}`) alongside it, since it isn't a first-class Spaces primitive. **Do not reach for PartyKit** for this either - see the correction under #50; it's been dormant since mid-2025. Pattern: throttle cursor broadcast via `requestAnimationFrame` (not raw `pointermove`); render remote cursors as absolutely-positioned overlays keyed by userId; fade/remove after a few seconds of silence; assign stable per-user colors (hash userId → palette index) so cursors are recognizable session to session. Spaces bills as a layer on top of Ably's core connection/message pricing, so cost compounds if also running #25 on the same plan - budget accordingly, it's still cheaper than a second vendor.
**Complexity tier:** medium if presence infra already exists for #50, medium-high to stand up alone just for this.
**Page types:** SaaS, Internal.

### 25. Real-time inventory streaming (events)
Live ticket/seat availability so two buyers don't both think they got the last seat. Server→client only (no client writes needed for the display itself), which makes **Server-Sent Events (SSE)** the right default tool over WebSockets for a standalone v1 - native browser `EventSource` API, automatic reconnection built in, no extra client library or vendor account, and it works with Vercel's serverless model where long-lived WebSocket connections don't (functions recycle after the request ends). A Route Handler streams a `text/event-stream` response, pushing inventory deltas on write from the DB's change stream or a pub-sub layer (Supabase Realtime, Postgres `LISTEN/NOTIFY`). **Upgrade to Ably** (the same account as #48, if that's also being built for this product) once the event page also needs presence/collaboration features or true public high-fan-out scale - Ably's consumption pricing (~$2.50/million messages, ~$1/million connection-minutes) scales cleanly with public fan-out, its SDK multiplexes multiple realtime features over one connection (avoiding SSE's ~6-connections-per-tab browser ceiling), and Ably (not a Vercel function) owns the persistent connection so this sidesteps the serverless long-lived-connection problem entirely. Either way, the actual write-path (the purchase itself) still needs a real transaction with row-level locking or optimistic-concurrency versioning at the DB (a `version` column, conditional `UPDATE … WHERE version = $x`) - the realtime layer is only the broadcast, it doesn't solve the race condition on "who actually gets seat 12." Fall back to short-interval polling for the simplest possible v0 if true sub-second updates aren't required yet.
**Complexity tier:** medium (SSE v1), medium-high (Ably, once #48 is also in scope).
**Page types:** Event.

### 47. Interactive reverse-chronological time travel
A draggable timeline slider that makes a SaaS dashboard visually "rewind" to how it looked/operated at a past minute. **Honest framing**: this is not literal UI state rewind - it's event-sourcing (or periodic snapshotting) plus a query parameterized by `as_of` timestamp, re-rendering the *existing* dashboard UI against historical data. Two buildable patterns: (1) **snapshot + delta replay** - persist periodic full snapshots plus an append-only event/audit log between them; "time travel" to `T` = load the nearest snapshot ≤ `T`, replay events up to `T`; (2) **time-series query with an `as_of` param** - if metrics already live in a time-series store (TimescaleDB, ClickHouse, InfluxDB), just re-run the existing dashboard queries with a historical time-window filter, no custom replay engine needed. This is the cheap version and covers most "metrics looked weird yesterday" cases. The slider drives a single `asOf: Date` value in URL/query state (`nuqs` or `useSearchParams`); every widget refetches keyed on that value; animate the transition with a cross-fade rather than trying to literally morph chart shapes. Don't build a generic "rewind the whole app" engine - scope it to specific metrics/tables that already have historical data available.
**Complexity tier:** low if metrics are already time-series (just add the `as_of` UI), very high if retrofitting event-sourcing onto an app that only stores current state.
**Page types:** SaaS, Internal.

### 36. Offline/reconnecting banners
A persistent, honest signal when the connection drops and when it's restored. If TanStack Query is in the stack, use it - it auto-pauses queries when offline and resumes on reconnect via its `onlineManager`, exposing `fetchStatus === 'paused'` as the exact signal to drive banner visibility, with a custom async reachability check beyond the default `navigator.onLine` (which only reflects OS network-adapter status, not actual internet reachability). Without TanStack Query: `window.addEventListener('online'/'offline', ...)` plus a periodic lightweight `fetch('/api/health')` ping to catch the "adapter connected, internet dead" case `navigator.onLine` misses. UX pattern: slide-down banner ("You're offline - changes will sync when you reconnect"), auto-dismiss with a brief "Back online" confirmation on reconnect, not a silent disappearance. Queue mutations locally (TanStack Query's mutation persistence, or a simple array) and flush on reconnect rather than failing silently.
**Complexity tier:** low.
**Page types:** SaaS, Landing (form-heavy pages benefit too).

### 33. Wasm-powered offline utilities
Client-side heavy compute - image compression, PDF generation/manipulation, CSV parsing at scale, in-browser hashing/crypto - that runs entirely in-browser without a server round-trip. Genuinely worth it for CPU-heavy, privacy-sensitive operations (a 2026 State of WebAssembly survey found 67% of respondents now run Wasm in production); a client-side PDF redaction/merge tool that never sends a document to a server is a real positioning fit for a security-focused company. Overkill for simple string/array operations or small-payload JSON work, where the JS↔WASM boundary-crossing overhead exceeds the compute saved - profile first, don't reach for it by default. Don't hand-write Wasm - use existing compiled libraries via dynamic `import()`: `@jsquash/*` for image codecs (WebP/PNG/AVIF); for PDF work, skip `pdf-lib` itself (no release since 2021, effectively unmaintained) in favor of the actively-maintained fork `@cantoo/pdf-lib`, or `mupdf` (MuPDF.js) for heavier rendering/parsing so the binary only loads on the route that needs it, run in a Web Worker to keep the main thread free, combine with #52's local-first storage so results persist offline.
**Complexity tier:** medium (mostly integration against existing WASM packages, not writing WASM).
**Page types:** SaaS, Internal, All (a client-side "compress this screenshot before upload" utility fits a landing-page contact form too).

## Cluster H - Localization, Events-Specific & Delight

Covers items #21, #29, #34, #38, #42. Treat #38 as non-negotiable (accessibility/legal exposure for a security-credibility brand); treat #42 as a flagship-event-only investment, not a default.

### 21. Dynamic localization routing
**next-intl** is the 2026 default for App Router i18n - built for Server Components from the start (translations resolve server-side with zero client-JS cost for static text), integrates with `proxy.ts` for locale negotiation/redirects in one config file, typed translation keys end-to-end (`next-i18next` is Pages-Router-legacy; no reason to reach for it on a greenfield App Router site). Pattern: root `app/[locale]/layout.tsx`, next-intl's `proxy.ts` middleware for locale detection (`Accept-Language` header → cookie fallback), `useTranslations()` in Server Components, `generateStaticParams()` per locale for static generation, `alternates.languages` in the Metadata API for correct `hreflang` per page. Don't force geo-IP redirects - Google explicitly penalizes auto-redirect-without-user-choice for SEO/crawlability; show a dismissible "switch to [locale]?" suggestion banner instead and let crawlers/users reach every locale directly by URL. Every locale needs its own canonical, not a shared one. Pair with locale-aware number/currency/unit formatting (`Intl.NumberFormat`) - pricing/dates/units silently staying in the wrong format after a language switch is a common half-finished-i18n bug.
**Page types:** All (highest value on Landing/Event for international reach).

### 29. Dynamic event timezone shifting
The **Temporal API reached Stage 4 / shipped in ECMAScript 2026** - native in Chrome 144, Firefox 139, Edge 144; Safari is Technology Preview only as of mid-2026, so production code still needs `@js-temporal/polyfill` (~100KB) for full cross-browser `Temporal.ZonedDateTime` arithmetic. If only *display* formatting is needed (no arithmetic/DST math), skip the polyfill and use native `Intl.DateTimeFormat(locale, { timeZone })`, universally supported for years. Store every event timestamp as UTC ISO-8601 + an IANA timezone string (`"America/New_York"`) at the data layer - ties directly to item #26's JSON-LD requirement for explicit UTC offsets. Render the **venue-local time** on the server (hydration-safe, no client/server mismatch); after mount, detect the visitor's zone via `Intl.DateTimeFormat().resolvedOptions().timeZone` and offer a toggle ("Show times in venue time / my time") rather than silently swapping, which causes a visible content flash and undermines trust on a ticketing/RSVP flow. DST transitions are exactly the bug class Temporal exists to kill - don't hand-roll offset arithmetic for multi-day events spanning a DST boundary.
**Page types:** Event (primary), SaaS (dashboards with distributed teams).

### 42. Spatial "choose your seat" venue map
Two viable tiers - pick based on how much this event page needs to be a flagship differentiator vs. a functional ticket flow. **Pragmatic 2D (recommended default)**: an interactive SVG venue map, clickable `<path>`/`<g>` seat zones, CSS `:hover`/`:focus` states, and a simple `StereoPannerNode` (L/R only, one trivial Web Audio API call) for a one-second audio preview of "how close to the stage this sounds." This is what most real ticketing platforms actually ship - cheap to build and maintain, fully screen-reader-friendly with an ARIA-labeled list-view fallback. **Full 3D**: `react-three-fiber` + `@react-three/drei`, a GLTF/Draco-compressed venue model, raycasting for seat selection, and true `PannerNode` 3D positional audio (position mapped from the seat's 3D scene coordinates). A multi-week build with a real asset pipeline (Blender export → Draco compression) and genuine mobile-perf risk for a Three.js scene on mid-range phones. Whichever tier is chosen, a **non-visual list-view of the same seat data is mandatory, not optional** - a purely visual/spatial map with no fallback fails WCAG operability outright and blocks screen-reader and motor-impaired users from buying a ticket.
**Page types:** Event only.

### 38. Accessible layout resiliency
Two concrete, testable WCAG AA success criteria, not a vague "be accessible" gesture. **1.4.4 Resize Text**: the page must survive 200% browser zoom with no loss of content/functionality - size type with `rem`, not `px`, so it scales with the browser's zoom/base font setting; use `clamp()` for fluid type; never `overflow: hidden` a text container sized for one zoom level. **1.4.10 Reflow**: at 400% zoom (a 1280px desktop viewport effectively becomes ~320px of usable width), content must reflow to a single column with **no horizontal scrolling** required - test via Chrome's actual zoom-to-400%, not just responsive breakpoints, since zoom and viewport-resize are different code paths and a site can pass one and fail the other. Fixed-height buttons/cards/nav items are the most common failure - use `min-height`, not `height`, wherever text lives; pair with `@container` queries so components reflow based on their own box, not just the viewport.
**Page types:** All - compliance/legal-risk mitigation as much as UX, which matters disproportionately for a security-credibility brand.

### 34. ASCII art console easter egg
Precedent: Facebook, Linear, Sentry, and Basedash all ship a styled `console.log` message. Technique is the `%c` CSS-directive format specifier - `console.log('%c...ascii...', 'font-family:monospace;color:#...')` - CSS applies to everything after each `%c` token, and monospace is required or the ASCII art collapses. Generate the logo's ASCII art once at build time (`figlet-cli` converts text/wordmarks to ASCII), embed it as a static string constant, fire it from a tiny client component mounted once in the root layout - not regenerated at runtime. On-brand twist for a security company: below the art, add a plain-language warning that pasting code into devtools is a self-XSS/social-engineering vector, never a legitimate "unlock a feature" step (Facebook's own precedent) - for Cybercom this reads as credibility, not just decoration. This is the one item on the list where the failure mode is a real security bug, not just a bad look - audit that no *other* `console.log` in the codebase leaks tokens, internal API payloads, or stack traces in production; the easter egg should be the only intentional console output. A second, harder-to-find interaction easter egg (e.g., typing `sudo` anywhere unlocks a terminal-style overlay) fits a security/brutalist brand better than a Konami code and reuses the same "console-first audience" insight.
**Page types:** All - near-zero cost, pure brand delight.

## Cluster I - Comprehensive Tracking Coverage

Covers item #4. Part 1 §7 already picked the tools (Plausible + PostHog) and the compliance frame (DPDPA). This is about **instrumentation completeness** - most sites only autocapture pageviews and clicks, then wonder why funnels have holes.

### 4. Tracking Everywhere
**Coverage checklist**, each buildable independently:
- Pageview + SPA route-change - App Router transitions don't fire a native pageview; capture explicitly on `usePathname()`/`useSearchParams()` change in a client component mounted in `layout.tsx`.
- Click autocapture (on by default) **plus** manual high-value CTA events (`cta_clicked`, props `{ cta_id, section, variant }`) - autocapture alone can't tell you *which* "Book a demo" button among five fired.
- **Rage clicks & dead clicks**: PostHog's autocapture layer detects both natively - dead clicks (a click triggering no DOM/state change) via `capture_dead_clicks: true`; rage clicks (rapid repeated clicks, a frustration signal) flagged automatically in session replay/heatmaps. Exclude deliberately-repeatable controls (steppers, upvote buttons) with the `.ph-no-rageclick` class; there's no per-element dead-click exclusion equivalent yet, so treat dead-click data as a heatmap signal, not a precise metric.
- Scroll depth + section dwell time via `IntersectionObserver`, not scroll-position math:
```tsx
function useSectionView(id: string, threshold = 0.5) {
  const ref = useRef<HTMLElement>(null);
  useEffect(() => {
    const el = ref.current;
    if (!el) return;
    let enteredAt = 0;
    const obs = new IntersectionObserver(([entry]) => {
      if (entry.isIntersecting) {
        enteredAt = Date.now();
        posthog.capture('section_viewed', { section: id });
      } else if (enteredAt) {
        posthog.capture('section_dwell', { section: id, ms: Date.now() - enteredAt });
      }
    }, { threshold });
    obs.observe(el);
    return () => obs.disconnect();
  }, [id, threshold]);
  return ref;
}
```
- Form field focus/blur-without-fill (abandonment), submit attempt vs. success vs. validation-error, and double-submit telemetry (pairs with item #8).
- Outbound link clicks and file/PDF downloads (autocapture misses these unless explicitly configured - add a `data-outbound` attribute convention and a delegated click listener).
- Copy events on pricing/code blocks (`copy` listener → `content_copied`, props `{ block_id }`) - a strong intent signal on SaaS pricing tables.
- Video watch % (25/50/75/100 milestones) via throttled `timeupdate`.
- **Session replay**, sampled (not 100%) - `session_recording: { maskAllInputs: true, maskTextSelector: '[data-sensitive]' }`. PostHog masks all text inputs by default; `maskInputFn` lets you redact by pattern (e.g. an email regex) even in fields not marked sensitive. There's no built-in way to mask query strings in replay URLs - audit that no PII ever lands in a URL param on tracked pages.
- Error correlation - PostHog's native error tracking ties an error directly to the session replay, feature-flag state, and event trail active when it fired; pipe the Sentry error ID into a PostHog event property (`error_id`, Sentry already installed) so a funnel drop and an error spike can be cross-filtered in one view instead of two dashboards.
- UTM/referrer persistence across the session - PostHog handles this automatically via `$initial_utm_*` person properties; verify it survives the cookie-consent gate (Cluster A, item #1), and set up cross-subdomain persistence if `app.` and the marketing site share a root domain.

**Event naming taxonomy** - standardize now, before the second engineer joins:

| Pattern | Example | Notes |
|---|---|---|
| `noun_verb_past-tense` | `form_submitted`, `demo_requested` | consistent across the whole codebase |
| Props, not new event names, for variants | `cta_clicked {id, section}` not `hero_cta_clicked` | keeps Insights filterable instead of fragmented |
| Server-side events for money-path truth | `plan_upgraded` fired from the Server Action after Stripe confirms, not on client click | client events can fire on abandoned/failed flows |

**Gotchas**: autocapture generates enormous low-signal volume - budget PostHog's event quota accordingly and use `before_send` to drop noisy internal-only events before ingestion. Every listener here must fire only after DPDPA consent per Part 1 §7 and Cluster A item #1 - gate `posthog.init()`'s autocapture and session recording behind the same consent gate as the initial pageview, not just the pageview itself. Rage/dead-click detection is a session-replay/heatmap feature, not (yet) a clean queryable Insights metric with per-element suppression - don't build a dashboard KPI on dead-click count without accepting some noise. Reuse one `IntersectionObserver` instance with multiple targets for long pages (dozens of sections) instead of one observer per section.
**Page types:** All (event-taxonomy and consent gating apply everywhere; scroll/dwell and video-watch tracking matter most on Landing and Event; form-abandonment and error-correlation tracking matter most on SaaS).

### Bonus ideas surfaced during research (use whenever relevant)

Not part of the original 56, but each of these fell directly out of researching them and is worth keeping on the menu:

- **`security.txt`** (`app/.well-known/security-txt/route.ts`, per RFC 9116) - a machine-readable vulnerability-disclosure contact. Near-zero cost, high credibility signal for a security company; pairs with Cluster A.
- **A public warrant-canary / trust page** - a periodically-updated statement of what legal requests have (not) been received. Optional, but on-brand for a security-positioned company; treat as a legal-review item before shipping, not an engineering one.
- **An SBOM/dependency-transparency ticker** - surface the output of the Knip/Dependabot/Socket.dev pipeline already mandated in Part 1 §2 as a public "here's what we run and how current it is" page. Turns existing CI hygiene into a trust artifact for free.
- **A live usage-meter widget** for SaaS billing pages (API calls, seats, storage against plan limits) - pairs naturally with #47's time-series infra and #19's optimistic updates.
- **A webhook-delivery console** for SaaS/Internal - recent deliveries, response codes, one-click replay. A recurring "we built this eventually anyway" feature for any product with outbound webhooks; worth scoping early rather than bolting on later.
- **Apple Wallet / Google Wallet passes for event tickets** (`PassKit`/`Google Wallet API`) - meaningfully reduces no-shows and support tickets ("I lost my ticket email") versus a PDF attachment; pairs with #26's Event schema and #29's timezone handling.
- **Arcjet × PostHog bot-filtered funnels** - Cluster B's bot-tier classification (item #2) means funnel/conversion data can be cleanly split into human vs. good-bot vs. bad-bot traffic at the source, rather than trying to filter bot noise out of analytics after the fact. Worth wiring once both tools are in place, since it's a few lines of shared context, not a new system.

| Large multi-file feature build where output risks getting truncated or half-finished | `full-output-enforcement` | Bans placeholder/`// ...rest of code` patterns common in big generations |

**Practical sequencing for a brand-new page** (ties Parts 2-4 together): (1) `imagegen-frontend-web` + Higgsfield to get section-by-section reference images → (2) `industrial-brutalist-ui` or `design-taste-frontend` to implement → (3) pull the relevant Part 2 clusters for the page type (Part 4 below has the checklist) → (4) `impeccable` for a polish pass → (5) `run` to verify in a real browser → (6) `security-review` if the page touches auth, tracking, or user input.

# Part 4 - Page-Type Playbooks

Each playbook pulls the applicable items from Part 1 (always mandatory) and Part 2 (the R&D menu, tagged by page type) into a build-order checklist. "Menu" items are exactly that - pull them in when the specific project justifies the cost; they are not a mandatory bar every page must clear.

## Landing Page (marketing, company/product pages)

**Mandatory (Part 1):** Metadata API + `metadataBase`, OG images, JSON-LD (Organization/WebSite), sitemap/robots, Core Web Vitals discipline (`next/image`, `next/font`, Server Components for primary content), full security-header set, Plausible + PostHog with consent gating, DPDPA-compliant Privacy/Terms.

**Menu, roughly in priority order:**
1. Icon/manifest matrix + OG completeness (Cluster B #3) - cheap, do it on every page.
2. Custom 404 + static 5xx fallback (Cluster C #7/#30) - cheap, do it once, reused sitewide.
3. CLS discipline - width/height, alt text, avif/webp (Cluster C #9) - non-negotiable, lint-enforced.
4. Accessible layout resiliency (Cluster H #38) - 200%/400% zoom testing - non-negotiable for this brand.
5. Bot policy - good-bot allowlist + Arcjet enforcement (Cluster B #2).
6. Noopener sanitization + `rel` hygiene (Cluster A #10/#28) - cheap, lint-enforced.
7. Intentional focus states + dark-mode contrast guards (Cluster D #40/#23).
8. Scroll-driven micro-animations (Cluster D #15) - native CSS, cheap once the pattern exists.
9. Comprehensive tracking coverage (Cluster I #4) - at minimum pageview, CTA clicks, scroll depth, form abandonment.
10. ASCII console easter egg (Cluster H #34) - near-zero cost, do it.
11. Command palette (Cluster E #17) - nav/search fallback, cheap once built once, reusable across every future page.
12. Semantic search via Pagefind, if a blog/docs surface exists (Cluster B #12).
13. GSAP scroll timeline set-pieces (Cluster D #20), sound UI (Cluster D #16/#53), dynamic localization routing (Cluster H #21) - reach for these when the project brief specifically calls for a flagship/high-production page, not by default.
14. AI speech bot / AI concierge (Cluster F #31/#41), dynamic personalization (Cluster F #13) - genuinely optional, budget-gated; use the MVP cuts documented in Cluster F before considering the expensive tier.

## SaaS Product Page / Dashboard

**Mandatory (Part 1):** Zod at every Server Action/Route Handler boundary with independent auth+authz, `server-only` DAL, rate limiting (Arcjet), nonce-CSP (no static/ISR trade-off to manage here - SaaS is dynamic anyway per Part 1 §"Details"), Sentry across all three runtimes, design tokens from the shared `@theme` layer.

**Menu, roughly in priority order:**
1. Loading state discipline - local pending states (Cluster C #11), skeleton placeholders sized to real content (Cluster C #27), route-level `loading.tsx` only where genuinely justified (Cluster C #5).
2. Optimistic UI updates via `useOptimistic` (Cluster C #19) - apply everywhere a mutation has a visible UI echo.
3. Double-click prevention + form semantics (Cluster E #8) - every form, no exceptions.
4. Custom error/status pages including `forbidden()`/`unauthorized()` (Cluster C #7).
5. Offline/reconnecting banners (Cluster G #36) - cheap, do it once TanStack Query (or equivalent) is in place.
6. Passkeys + social login (Cluster A #14) - ship additive to password auth, don't force a cutover.
7. Comprehensive tracking coverage, SaaS-weighted toward form abandonment and error correlation (Cluster I #4).
8. Command palette + keyboard speedrun shortcuts sharing one hotkey registry (Cluster E #17/#32).
9. Instant content previews via hover-card / intercepting routes (Cluster E #18).
10. Dark-mode contrast guards + intentional focus states (Cluster D #23/#40) - SaaS surfaces get heavier daily use than marketing pages, so accessibility debt compounds faster here.
11. Instant local-first architecture (Cluster C #52) - only once a specific page's UX is bottlenecked on network round-trips; run the "what's allowed to live in local storage" security review first.
12. Vim-mode navigation for data-dense views (Cluster E #51), contextual command execution (Cluster E #44), zero-delay ghost previews for settings/automation UIs (Cluster E #46) - power-user tier, scope to the specific dashboards where daily-active users will actually benefit.
